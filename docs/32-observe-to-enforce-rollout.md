# 32 站点 observe → enforce 上线流程（提案，待产品决策）

状态：**提案，未实现**。docs/00 §0.3 已定“新接入先 observe 验证，再 enforce；产品目标为强制模式”，但今天只有请求加密一层有 observe（docs/08：`OBSERVE` 透传并记录候选，不解密）。站点级的“先观察、后强制”没有状态、没有审计词汇、没有退出标准，所以新站点只能直接 enforce，或手工把路由放成 `PUBLIC`。本文给出一个可评审的最小设计，并把需要产品负责人拍板的问题单列出来。

## 32.1 要解决的问题

接入一个已有应用时，运营者无法在不影响真实用户的前提下知道：哪些页面操作没有被声明、哪些列表会签发资格、哪些请求会被 `UI_ACTION_NOT_AVAILABLE`/`CAPABILITY_MISSING` 拒绝。直接 enforce 会把配置遗漏变成线上故障；长期 `PUBLIC` 则让站点实际上没有防护。需要一个**有期限、有证据、可审计**的过渡状态。

## 32.2 不变量（任何实现都不得违反）

1. 模式只来自服务端配置的已批准修订；客户端删 Cookie、改版本、禁用 JS、带任何头都不能选择或改变模式（沿用 docs/00 §0.3）。
2. 默认就是 enforce：配置里没有该字段、解析失败、不认识的取值，一律按 enforce 处理；observe 必须显式声明。
3. observe 不改变认证与资格的**真值**：身份绑定、资源资格、页面签发的存储与校验照常进行；observe 只改变“本应拒绝的请求是否仍被转发”，且每一次都落审计。
4. 状态变更方向不对称：observe → enforce 是收紧，enforce → observe 是放宽。放宽必须独立审批，且不能被 `apply_direct` 豁免（与 `AUTH_ENTRY_CHANGED` 等风险令牌同一规则）。
5. observe 有期限。到期不得静默延续：按 32.5 的选项落到 enforce 或暂停，不能停在 observe。
6. 模型与 Agent 不能把一次本应拒绝的请求改判为放行（AGENTS.md：模型不能绕过确定性拒绝）；observe 记录的是确定性规则的判定，而不是模型意见。

## 32.3 建议的模型

- `SiteConfig.rollout`：`{ mode: "observe" | "enforce", observe_until: <UTC 秒>, scope: "site" }`；缺省 enforce。路由可以单向覆盖为 enforce（站点 observe 时，已验证的路由先收紧），不能把 enforce 的站点局部放宽。
- 风险令牌 `ROLLOUT_MODE_RELAXED`（enforce→observe、延长 `observe_until`、把路由从 enforce 放回 observe）需要独立审批；`ROLLOUT_MODE_TIGHTENED` 不需要额外审批但必须有审计。
- edge 编译同一份配置：observe 时对每个会被确定性规则拒绝的请求，仍执行“判定 + 审计”，然后按透传流程转发；`request.completed` 的决策值新增 `OBSERVED_WOULD_DENY`（带原本的稳定原因码），并携带 `rollout_revision`。**这需要升级审计契约（docs/11）与 worker 的封闭解析器**，沿用此前 `gateway_audit.rs` 的做法：先写解析器与变异测试，再改 edge。
- 请求加密已有的 `OBSERVE` 保持不变，仍是路由级的独立开关；本文不改它。

## 32.4 退出标准（由控制面计算，不由运营者填写）

控制面在发布页显示“可以收紧吗”的报告，数据来自 ClickHouse 索引的结构化检索（沿用既有查询与审计）：

- 观察窗口长度（建议默认至少 7 天，可配置下限）与期间的请求总数；
- `OBSERVED_WOULD_DENY` 按原因码、按路由的计数与占比，以及最近一次出现的时间；
- 仍未被任何路由或页面动作覆盖的端点清单；
- 索引水位与待发布段（审计没有跟上时报告标为“不足以判断”，不是“通过”）。

报告只给事实；是否收紧仍由审批人决定，批准写入“依据哪一份报告摘要”。索引读不到时界面写明“无法判断”，不用 0 代替。

## 32.5 需要产品负责人决定的问题

1. **observe 是否允许转发本应被拒的请求？** 这是 observe 的价值，也是最大的风险（源站会收到未经资格校验的请求）。保守方案：只对 `PUBLIC` 之外且**只读（GET/HEAD）**的路由允许；写操作在 observe 下仍拒绝。
2. **到期行为**：自动转 enforce（可能造成线上故障）、自动暂停站点（可能造成不可用），还是只告警并拒绝再次申请 observe？建议“到期自动转 enforce，到期前 24 小时起告警”。
3. **粒度**：站点级加路由单向收紧（本文建议），还是纯路由级？
4. **观察数据的保留与脱敏**：`OBSERVED_WOULD_DENY` 事件沿用现有脱敏与保留期；是否需要更长保留期用于上线评审？
5. **谁可以放宽**：沿用站点审批角色，还是要求更高角色？

## 32.6 实施顺序与验证

1. 审计契约与 worker 解析器（先失败测试 + 变异测试），文档 docs/11。
2. core 模型与校验、风险令牌、控制面拒绝 `apply_direct` 豁免、迁移（若需要投影列）。
3. edge：observe 判定与转发、`rollout_revision`；真实二进制脚本断言（本应拒绝的请求在 observe 下到达源站且产生 `OBSERVED_WOULD_DENY`，在 enforce 下被拒，客户端无法选择）。
4. 控制台：向导“入口与模式”的 observe 选项、发布页退出报告、审批文案。
5. 运行：真实 ClickHouse 回归（本机原生 25.8，见 docs/20）与完整 `verify_all.sh`。

在 32.5 的问题定下来之前不开始实现；第 1 条与第 2 条的答案会改变 edge 与控制面的大部分设计。
