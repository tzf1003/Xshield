# `self` 档位的核验规则：修改方案（用户已同意方案 A）

- 日期：2026-11-13，基线 main `626722f`
- 状态：用户 2026-11-13 答复“按建议就行”，采用方案 A，现在开实现线程（第 9 节第 1、2 题）。第 3 题没有单独的建议，按最少的做：只写 CHANGELOG，不另发说明。本稿写成时没有改任何代码。
- 来历：验收“防护有效性验证”第一波时，用真实网关跑 clinic 靶场的良性流量量出来的（方案 `docs/design-records/plans/protection-effectiveness-plan.md` 第 12a 节）。

## 1. 结论

对象表里把响应位置标成 `self`（本人对象）之后，这个位置展示过的对象不再算“会话见过”，医生访问自己患者的请求从快速放行变成每次都问模型。建议改一处规则：**`self` 档位的响应和没有标档位的响应一样证明会话见过对象**。改动只有 `tier_proves` 里的一行，加上测试和文档。`self` 排除收紧的作用不变，收紧条件不变，提示词不变，配置和判定记录的字段不变。

## 2. 量到的数字

同一批良性流量：12 位医生各登录 4 次，1861 个请求，其中 1361 处是对本人对象的引用（自己的患者、就诊、处方）。真实 `xshield-edge`，理想模型 Jev，拦截模式。只换站点的对象表：

| 对象表 | 本人对象引用被核验 | 快速放行占比 | 每请求 Jev 调用 | 被拦 |
|---|---|---|---|---|
| 不声明（只有身份位置） | 1312/1361，96.4% | 80.4% | 0.20 | 0 |
| 按真值全部声明，`self` 位置可靠性 `high` | 98/1361，7.2% | 15.2% | 0.85 | 0 |
| 同上，但 `self` 位置可靠性改成 `medium` | 98/1361，7.2% | 15.2% | 0.85 | 0 |
| 同上，但去掉 `self` 标注（条目和类别保留） | 1361/1361，100% | 80.4% | 0.20 | 0 |

第二行里没被核验的 1263 处全部是本人对象：打开自己的患者 303、就诊 376、处方 392，改、删、分享自己的患者和打开刚新建的患者各 48。第四行说明原因只在 `self` 标注上：去掉它，核验率比不声明对象表还高（搜到的患者也核验了）。

没有被拦是因为靶场用的是理想模型，它对良性请求一律答放行。换成真实模型，这 1263 个请求的放行就取决于模型每一次的回答。

复现：`/mnt/project-files/acceptance/selftier/measure.py`（需要批次 2 的 clinic 靶场，PR #201）。

## 3. 原因

判定按来源响应的档位决定它是否证明会话见过对象。`crates/xshield-core/src/context/objects.rs` 的 `tier_proves`：

```rust
match tier {
    Some((Tier::Own, _)) => false,                       // self：任何可靠性都不证明
    Some((Tier::Admin, _)) => admin,
    Some((Tier::Public, Reliability::High)) => !closed,
    None | Some((Tier::Org | Tier::Public, _)) => true,  // 没有标档位：证明
}
```

没有标档位的响应证明，标成 `self` 的不证明。于是给“我的患者”加上 `self` 标注，等于收回了它原来就有的证明力。docs/07 §7.4.7 的表和 docs/01 §1.4 第 4 步写的也是这个行为，代码和文档一致，所以它不是实现写错，而是规则本身的问题。

这条规则和别处的说法对不上，共四处：

1. **用户 2026-11-03 确认的决定**（`docs/design-records/designs/ownership-tiers/handoff.md`）只有一条收紧条件：目标值只来自公共档，并且请求位置不接受公共来源，两边可靠性都高。另一条默认约定是“不带这些字段时行为不变”。这三条决定里没有“`self` 不再证明”这一项，它出现在 PR #165 的实现和文档里（提交说明写着“A self sighting never allows on its own”）。当时的讨论稿原文我没有核对。
2. **docs/07 §7.9.16** 说 `self`“只用来排除收紧，从不用来放行。误判只让位置维持现状”。实际上标注之后位置没有维持现状，而是失去了证明力。
3. **docs/07 §7.4.7** 说“判定只读可靠性为 `high` 的判断”，`Reliability::Medium` 的注释说它“不改变任何决定”。实测 `medium` 的 `self` 同样让核验率掉到 7.2%（上表第三行）。
4. **Jev 的指令**（`state.rs` 的 `ACCESS_INSTRUCTIONS`）告诉模型“Tier self 是会话自己的记录”。网关不肯核验、转交给模型，模型拿到的说明却是“这是本人的”，它会放行。这一趟模型调用没有带来新的判断。

## 4. 为什么每个按流程学习的站点都会碰到

`self` 不是可有可无的标注。学习“请求位置是否接受公共来源”时（`learning.rs` 的 `judge_accepts_public`），一票只有在它的来源位置里至少一个有已确认的档位时才计入。医生删除自己患者的票，来源是“我的患者”列表，这个列表不确认成 `self` 就不计票，`DELETE` 也就学不出“不接受公共来源”。

所以正常流程是：先确认 `self`，才能学出 `accepts_public: false`，才能拦“搜到别人的患者后删除”。走完这个流程的站点，本人对象的访问就全部改走模型。

## 5. 影响

- **费用和延迟**：这批流量的模型调用从每请求 0.20 次变成 0.85 次，约四倍。业务系统里“打开自己的东西”是最常见的请求。
- **误拦**：真实模型下，这些原本确定放行的请求改由模型判断。评审 P2-2 记录过真实模型 0.55 概率的拒绝；P2-2 的置信度门槛加上以后，低置信度的回答按 UNKNOWN 处理，这些请求受到的影响会更大。
- **可用性**：每个会话每分钟最多 60 次模型调用（docs/07 §7.6），超出按 `on_jev_unavailable` 处理（靶场配置是拒绝，项目规则不允许默认放行）。一个医生一分钟内翻 60 个以上自己的患者就会被拦。模型不可用时，本人对象的访问也全部失败，而不声明对象表的站点这时还能快速放行。这一条是按文档的限额推出来的，没有实测。
- **防护没有变强**：见第 6 节。

## 6. 方案

### 方案 A（建议）：`self` 和未标档位一样证明

`tier_proves` 里 `Some((Tier::Own, _)) => false` 改成 `true`（并入最后一个分支）。

改完以后的行为：

| 来源响应 | 收紧条件成立时 | 收紧条件不成立时 |
|---|---|---|
| `self`（现在） | 不证明 | 不证明 |
| `self`（方案 A） | 证明 | 证明 |
| 没有标档位（不变） | 证明 | 证明 |

`self` 排除收紧的作用不受影响：是否“尝试越权”由另一段代码算（`tiers.rs` 的 `public_only`，要求每个来源都是高可靠的公共档），它没有改。

**为什么不会多漏**。一个值在方案 A 下变成“已核验”，前提是某个标了 `self` 的响应位置曾经把它作为同类对象展示给本会话。同样的展示在标注之前本来就核验。分两种情况看：

- 标注正确（确实是本人列表）：值是会话自己的对象，应当放行。
- 标注错误（比如按查询返回、结果互不相交的搜索接口被学成了 `self`，docs/07 §7.9.16 提到过这种误判）：方案 A 下这个值被核验并快速放行，和标注之前一样漏。现在的规则下它不被核验，交给模型，而模型被告知“这是会话自己的记录”，也会放行。两种规则下都漏，区别只是现在多一次模型调用。真正的防线是管理员确认 `self` 提议这一步，方案 A 不动它。

所以现在的规则换来的防护接近于零，代价是第 5 节的全部。

**要改的文件**（一个 PR，判定路径改动）：

- `crates/xshield-core/src/context/objects.rs`：`tier_proves` 和它的注释、单测。
- `crates/xshield-judge/src/tiers.rs`：两个单测改预期（`a_self_sighting_never_allows_on_its_own_…`、`a_self_sighting_without_a_reliability_…`），改名为“self 的展示照常证明，并排除收紧”。
- `crates/xshield-judge/src/engine.rs`：`a_later_listing_of_the_sessions_own_patient_ends_the_attempt` 里 `assert!(!value.verified, …)` 改为断言已核验，并断言第二次删除走快速放行、不再调用 Jev。
- `crates/xshield-control/src/object_impact.rs`：确认提议前的影响预览用的是同一个 `tier_proves`，代码不用改；涉及 `self` 的测试预期要跟着改（确认 `self` 不再产生“退回 Jev”）。
- `scripts/test_idor_lab.py` 和 `tests/security-lab/`：现有靶场站点没有 `self` 位置。新增一个场景：声明“我的患者”为 `self`、`DELETE` 不接受公共来源的站点上，打开和删除自己的患者快速放行；搜到别人的患者后删除仍然是尝试越权并被拦；先搜到、再出现在自己列表里的患者可以删除。
- 文档：docs/01 §1.4 第 4 步、docs/07 §7.4.7 的表和下面一段、§7.9.16 的 `self` 一条，`CHANGELOG.md` 加一条。
- 不改：站点配置字段、判定记录字段和 schema、提示词（所以提示词版本号不变）、学习规则、控制台前端。

**检查**：按 AGENTS.md 判定路径一行执行，包括全量靶场。

### 方案 B：规则不动，在流程上绕开

学习不再提议 `self`，或控制台在确认时强提示影响（影响预览已经会显示“退回 Jev”的数量）。

不建议。不确认 `self` 就学不出 `accepts_public: false`（第 4 节），等于放弃“搜到后删除”的防护；管理员手写的 `self` 标注照样触发问题；第 3 节的四处矛盾还在。

### 方案 C：`self` 只在身份对得上时证明

比如要求会话有已声明的身份才让 `self` 证明。

不建议。没有标档位的响应并不要求身份就能证明，给 `self` 单独加条件仍然是“标了反而更弱”，而且要多一套规则和配置。它想防的标注错误，前面已经说明现有规则也防不住。

## 7. 验收标准

1. 复跑第 2 节的四种对象表：第二行和第三行的核验率不低于第一行，快速放行占比和每请求 Jev 调用回到第一行的水平（80.4%、0.20），四行都没有被拦。
2. 新增靶场场景全部通过，现有 150 项核对不变。
3. “搜到别人的患者后删除”在带 `self` 的站点上仍然被拦，判定记录里是 `attempt: over_privilege`。
4. 有效性验证里这件事由“按配置分开的 S1、S3、S4”来量（回归用例只看拦或放，量不出核验率）：修复前“真值”一列的 S1 约 7%，修复后不低于“无对象表”一列，并由只进不退的基线锁住。按配置分列由批次 4 加进评分器和报告。
5. Rust 检查、全量靶场、文档与行为一致。
