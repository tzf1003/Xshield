## 结论

1. **功能表段落的判定没有被带偏。** 77 条功能表用例的结论全部落在基线三遍出现过的结论之内，69 条必须符合的仍然全部符合。`access` 的 DENY 概率平均变动 0.011，最大 0.11（`POST /api/permissions/grant` 由 0.63 到 0.77 变为 0.59，仍拦）。
2. **长值切片后的越权判定正常。** 一份 state 装得下时（单个 1,500 字符的值切成 4 片），10 条全部符合预期，见第 2 节。
3. **发现一个缺陷：分批的请求，路径里带对象编号时会被误拦。** 第二批的 state 里没有路径编号那个值（它在第一批），`recent` 又被裁成 0 条，模型看到路径里的 `7005` 却找不到任何“已展示”的证据，`access` 答 DENY（0.86 到 0.92）。任一批判拒即拒绝，所以合法的多字段表单只要落在带编号的路由上、又需要两批以上，就稳定被拦。这正是批次 2 想修好的那类请求（问卷、批量编辑）。详见第 3 节。
4. 顺带观察：只靠路径的攻击探测，`attack` 的 ATTACK 概率比基线低了约 0.1（`/.git/config` 0.55 变 0.42，`/backup.sql` 0.52 变 0.42，`/h2-console` 0.34 变 0.24，商店的开放重定向 0.43 变 0.37）。只有一遍，这几条都由 `access` 判拒，结论没有变。批次 7 定置信度门槛时值得再看一眼。

## 3. 分批（10 次调用）和缺陷

请求体是 24 个 420 字符的字段加一个 1,500 字符的字段，分成 2 批，裁剪级别 3。

| 用例 | 预期 | 结果 | 各批的 `access` |
|---|---|---|---|
| P10 `POST /api/patients/7005/notes`，全部是正常文字 | 放 | **拦** | 第 1 批 ALLOW 0.98，第 2 批 **DENY 0.86** |
| P11 同上，另加没展示过的 `attachment_id` | 拦 | 拦 | 第 1 批 DENY 0.81（带那个值），第 2 批 DENY 0.92 |
| P12 管理档功能上的尝试越权 | 拦 | 拦 | 两批都 DENY 0.99 |
| P13 未知的普通功能 `POST /api/feedback` | 放 | 放 | 两批都 ALLOW 0.99 |
| P14 P10 加一条命令注入（落在第 2 批） | 拦 | 拦 | 第 1 批 ALLOW 0.99，第 2 批 DENY 0.91 且 ATTACK 1.00 |

P10 是误拦。原因在第 2 批的 state：

- `request.path` 是 `/api/patients/7005/notes`，各批相同。
- 已核验的路径值 `{"at":"path[2]","value":"7005","verified":true}` 只装进了第 1 批。
- 分批时裁剪级别为 3，`recent` 是 0 条，值的来源也不列。

模型在第 2 批里看到路径带一个编号，却没有任何一条说它展示过，于是答 DENY。P13 的路径里没有编号，同样形状的第 2 批就答 ALLOW，P10、P11、P14 的第 2 批都答 DENY，三次一致。指令里“只判断列出的值”那一句没能让模型不看路径。

**修法的验证（3 次调用）**：把第 1 批里那一个路径值原样补进第 2 批的 state 再问：

| state | 原来 | 补上路径值之后 |
|---|---|---|
| P10 第 2 批（问了两次） | DENY 0.86 | ALLOW 0.96、ALLOW 0.99 |
| P14 第 2 批 | DENY 0.91，ATTACK 1.00 | ALLOW 0.87，ATTACK 1.00 |

建议的修法：位置在路径里的值（`at` 以 `path[` 开头的）和 `function` 一样算请求自身的空壳，每一批都带上。它们数量很少，对每批的容量影响可以忽略。修好后把 P10 这样的用例放进 `live_jev.rs`，并在靶场里加一条假 Jev 的场景，核对每一批的 state 都带着路径值。

在修好之前的影响：正文超过一份 state（约 8 KiB）、路由里带对象编号的正常请求在拦截模式下会被拦。按批次 2 的说明，合入之前这类请求在 state 放不下时返回 403，所以多半不是变差，但批次 2 的目标在这类路由上没有达到。
