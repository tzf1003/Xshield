## 1. 结论

三层都能做，而且大部分能复用对象表、身份位置、档位学习和“尝试越权”这几套现成机制。建议分三步落地：

1. **第 1 层先做**，它独立、改动小：凭证没被源站认可之前，按“没有凭证”处理，只能访问入口。PR 193 只做了一半（不再为假凭证存会话），假凭证的请求现在仍然被快速放行，见第 2 节。
2. **第 2、3 层先上学习和控制台，不改判定**：控制面按用户和角色统计每个“功能”（方法加路由模板）被谁成功访问过，在控制台列出来，提议管理功能，并用已有的影响预估回放“如果启用，过去的请求里有多少会变”。
3. **看过数据再上判定**：管理员确认过的管理功能，非管理员访问就是尝试越权；功能表之外的功能不再快速放行，交 Jev。两者都靠站点配置开启，没开的站点行为与现在完全相同。

需要新增的东西：站点配置 `objects` 下一个功能表和一个开关，一次迁移（放宽一个现有表的取值约束），不新增表、环境变量和 crate。理由见第 12 节。

第 15 节的四个问题你在 11-13 都已答复。真实 Jev 的预检结果在第 16 节。

## 2. 现状（PR 193 之后）

临时测试的结果，拦截模式，测试站点的入口是 `/login`、`/api/home`、`/api/patients`、`/share/*`：

| 请求 | 不带 Cookie | 带 `SID=made-up` |
|---|---|---|
| `GET /metrics` | 401 `no_session` | `fast_allow`，0 次 Jev |
| `GET /api/admin/export` | 401 `no_session` | `fast_allow`，0 次 Jev |
| `GET /users/alice` | 401 `no_session` | `fast_allow`，0 次 Jev |
| `DELETE /api/patients` | `fast_allow`（见下） | `fast_allow`，0 次 Jev |

三点事实：

- **PR 193 解决的是 P1-8，不是 P0-3。** 它让假凭证在判定阶段不占会话槽、不拿独立的 Jev 额度。但假凭证的请求仍按“一个空会话”判定（`engine.rs` 的 `plan`，`turn.unconfirmed`），没有请求值时照样 `fast_allow`。
- **假凭证一个请求之后就有会话。** 上面被放行的 `/metrics` 请求一旦得到源站的 2xx，`observe` 就为这个凭证建会话；带假凭证访问 `/login` 页面也一样（探针里这两步之后网关各多出一个会话）。这就是 PR 193 留下的那个问题。
- **入口不分方法。** `DELETE /api/patients` 不带任何凭证也被快速放行，因为 `/api/patients` 登记成了入口，而入口只按路径匹配。登记“我的患者”列表为入口，等于同时开放了这个路径上的所有方法。

所以现在的功能级防护只有一条：没带凭证的请求不能访问非入口路径。其余情况下，路径和参数都是普通单词的请求，对任何带凭证的人都是零判定直通。

## 3. 范围和用词

**功能**：方法加路由模板，例如 `POST /api/admin/export`、`DELETE /api/patients/{id}`。路由模板沿用对象表位置的写法：逻辑路径（URL 路径加接口名，docs/07 7.4.7）先化为规范拼写，数字和 UUID 段换成 `{id}`（`path_template::position_template`）。用请求头或正文字段区分接口的站点，接口名已经在逻辑路径里，所以同样适用。

**管理员会话**：沿用现有定义，对象表的角色身份位置声明的标签是 `admin`（docs/07 7.4.7）。

纳入防护的三种情况：

| 情况 | 例子 | 由哪一层处理 |
|---|---|---|
| 没登录，带一个随手编的凭证调任意接口 | `SID=made-up` 访问 `/api/admin/export` | 第 1 层 |
| 普通用户调管理功能 | 医生会话调 `POST /api/admin/export` | 第 2 层 |
| 任何人调正常流量里没人走的功能 | `/metrics`、`/actuator/env`、`/ftp/` | 第 3 层 |

不纳入的写在第 11 节。

## 4. 第 1 层：凭证被源站认可才算会话

### 4.1 规则

凭证分两种状态：**未认可**和**已认可**（网关里有它的会话）。

未认可的凭证按“没有凭证”处理：

- 非入口路径返回 401，判定路径仍是 `no_session`。不再有“空会话”这个中间状态。
- 入口路径照常判定，上下文和 Jev 额度都用客户端地址的（额度这一点 PR 193 已经做了）。
- 判定记录与没带凭证的请求相同（会话标签为空），另在 trace 上加一个布尔字段 `unrecognized_credential`。这样现有查询里“会话标签非空即有会话”的含义不变，“带了凭证却没有会话”的请求也能单独数出来。

认可的依据，只认源站自己说的话：

| 编号 | 依据 | 现状 |
|---|---|---|
| S1 | **下发**：源站在响应里用配置的 Cookie 或响应头下发了这个凭证（登录跳转、凭证轮换） | 已有 |
| S2 | **登录绑定**：JSON 登录响应里出现过这个凭证（docs/01 1.7 的待绑定登录） | 已有，但只在入口请求上尝试 |
| S3 | **身份声明**：对象表的身份位置所在的响应，为这个凭证声明了用户 | 身份已有，用作认可依据是新的 |
| S4 | **入口应答**：源站对带这个凭证的入口请求答了 2xx | PR 193 的做法（它对任意路径都算） |

### 4.2 对 PR 193 遗留问题的处理

遗留问题是 S4 太弱：登录页这类公开入口对谁都答 2xx，它的 2xx 不说明凭证是真的。处理分三条：

1. **未认可的凭证到不了非入口路径**（4.1），所以“任意路径的 2xx”这个口子自然收窄成“入口的 2xx”。观察模式下，本应拦截的请求的响应不算认可。你已经同意这类响应不再学习（P1-5），认可凭证按同一条原则处理。
2. **声明了用户身份位置的站点不用 S4。** 这类站点有更强的依据：身份接口对假凭证返回的是空用户，不会声明身份。所以只认 S1、S2、S3。假凭证访问多少次公开入口都没有会话。
3. **没有身份位置的站点保留 S4。** 这类站点没有别的办法在网关重启后认回老会话，去掉 S4 会把在线用户锁在外面（见 8.1）。代价是遗留问题在这类站点上还在：编一个凭证，先访问一次公开入口，就有会话。它之后能走到哪里由第 3 层兜底。控制台的就绪检查对这类站点显示一条提示：“未声明身份位置，编造的凭证访问一次入口即成为会话”，修法就是声明身份位置。

另外两处配套改动：

- **S2 不再限于入口请求。** 现在 JSON 凭证站点登录后的第一个请求必须落在入口上才绑定（docs/01 1.7）。第 1 层之后，没绑定上的凭证是未认可的，第一个请求落在别处会直接 401。绑定只是一次哈希比较，PR 193 之后没有会话的凭证也不再有“会话已存在”的顾虑，所以改成任何路径上的第一个请求都尝试绑定。这同时去掉了一条现有的接入限制。
- **凭证刷新要能认。** 带旧凭证的请求得到新凭证时：Cookie 轮换走 S1，已经能认；JSON 刷新接口返回的新令牌现在不暂存，新令牌会是未认可的，每个刷新周期全员 401。这就是 P1-1，必须在第 1 层之前或同时修（带凭证请求的 2xx JSON 响应也暂存候选，绑定时继承旧会话）。

### 4.3 一个要说清楚的局限

很多用服务端会话的框架（PHP、Java、ASP.NET）给每个匿名访客都发会话 Cookie。在这类站点上，访问一次登录页就能拿到一个源站真的下发过的凭证（S1）。所以**第 1 层挡的是“编造的凭证”，不是“没登录的人”**。匿名会话和登录会话的区别只有身份位置能说明，功能级的区分靠第 2、3 层。

## 5. 第 2 层：管理功能只给管理员会话

### 5.1 学习

学习任务已经在按“单位”（声明了用户身份的站点按用户，否则按会话）读判定记录。新增按功能的统计，窗口沿用 7 天：

- 管理员单位在这个功能上得到放行且源站答 2xx 的个数；
- 非管理员单位同样成功的个数；
- 非管理员单位在这个功能上被源站拒绝（401、403）的个数；
- 窗口内全站活跃的非管理员单位数。

提议一个功能为**管理档**的条件：至少一个管理员单位成功过；没有任何非管理员单位成功过；并且下面两条至少满足一条，说明“非管理员没走过”不是因为没人：非管理员被源站拒绝的单位数达到阈值（`objects.learning.thresholds.sessions`，默认 5），或全站活跃的非管理员单位数达到阈值。入口不提议。

可靠性沿用现有的三档：证据达到阈值的两倍、且管理员在不少于两天里用过，为 `high`；达到阈值为 `medium`；站点没有用户身份、只能按会话统计时降一档；`low` 不提议。

提议走现有的“学习提议，管理员确认”的流程，不自动生效。驳回后同一提议不再出现。

这条规则和现有的响应位置管理档（docs/07 7.9.16）不同的地方：现有规则要求有足够多的非管理员被源站拒绝，也就是源站自己在拦。功能级越权恰恰是源站没拦、界面上只是不显示按钮的情况，所以这里允许用“全站有足够多的普通用户在活动，但没有一个人走过它”作依据。这个依据比被拒绝弱，会把“普通用户也能用、只是这周没人用”的冷门功能提议成管理档，所以必须由你确认。

### 5.2 配置

对象表现在的条目是“位置”（某个接口里的某个值），必须带类别，装不下“一个接口本身归谁用”。在 `objects` 下新增一个列表：

```json
"objects": {
  "functions": [
    { "key": "POST /api/admin/export", "source": "rule", "tier": "admin", "reliability": "high" },
    { "key": "GET /api/patients", "source": "rule" }
  ]
}
```

`key` 是方法加路由模板；`source`、`tier`、`reliability` 沿用位置条目的字段和取值。功能条目没有 `paused`：目前没有自动暂停，想停用管理档时删掉 `tier` 即可，条目仍是已知功能（细化实现规划时去掉的）。`tier` 现在只接受 `admin`，省略表示这个功能对所有会话开放。不带 `tier` 的条目是第 3 层用的“已知功能”。取名 `functions` 是因为顶层的 `routes` 已经被接口名规则占用。

### 5.3 判定

请求的功能按现有的位置定位规则找条目：精确匹配优先；条目里的 `{id}` 可以覆盖任意一个非空段，字面段多的优先，一样多时带管理档的优先。

命中的条目是管理档、可靠性 `high`，而会话不是管理员会话（包括没声明过角色的会话、地址上下文）时，这个请求是**尝试越权**：

- 不快速放行，不查也不写放行缓存，**即使请求里的值全部核验过**。普通用户拿自己的编号调 `PUT /api/admin/users/{id}/role`，值是见过的，功能不是他的。
- 交 Jev，`state.request` 带上 `"function": {"tier": "admin", "attempt": "over_privilege"}`，指令要求答 DENY。这沿用 11-03 定下的做法（尝试越权交 Jev 并要求 DENY，网关不直接拒绝）。如果以后想改成网关直接拒绝，值的尝试越权和功能的尝试越权应该一起改。
- 判定记录写 `trace.function`（功能键、档位、是否尝试越权），就绪检查据此计数。

管理员会话访问管理功能，按正常逻辑判，与没有这条规则时相同。角色仍然不是放行理由。可靠性不是 `high` 的条目不参与判定。

带方法覆盖的请求（`X-HTTP-Method-Override`、`X-HTTP-Method`、`X-Method-Override` 头，或查询串、表单里的 `_method`）按每个方法各定位一次，取更严的结果，免得用 POST 绕开 DELETE 上的管理档。传输方法先转成大写再查。路径的规范拼写里还留着 `%2F` 或 `%5C` 时，换成 `/` 再查一次，同样取更严的，免得源站先解码再路由时条目被绕开。细则见 T4 规划 2.2。

## 6. 第 3 层：功能表之外的功能交 Jev

### 6.1 已知功能

网关需要知道“本站正常流量里有哪些功能”。这份清单就是 5.2 的功能表：不带 `tier` 的条目是已知功能，带管理档的条目当然也是已知的。另外，对象表里声明过位置的接口，它的功能自动算已知，不用重复登记。

基线从学习来：功能在窗口内被放行且源站答 2xx 或 3xx，就记一次“走过”，按单位计数。控制台的功能表页列出学到的全部功能和各自的单位数，达到阈值（默认 5 个单位）并且名字不敏感的默认勾选，其余不勾选，由你一次确认写入配置。名字敏感指路径里带 `admin`、`metrics`、`actuator`、`debug`、`export` 这类词：它们即使很多人走过也不默认勾，因为一旦进了基线，第 3 层就不再管它（写控制台规划时定的，见 function-level-authz-plan-functions-console.md 2.3）。只有管理员走过的功能在这里会同时显示管理档提议。

入口不自动算已知。入口上实际被走过的方法会出现在基线里（没带凭证的入口请求按客户端地址计单位），没人走过的方法不会，所以第 2 节里对入口路径发 `DELETE` 的问题由这一层处理。

基线确认之后，新出现的功能（源站发版）以提议的形式出现在控制台，确认后加入，不自动加入（你在 11-13 的决定）。已知功能不自动过期：月结、年报这类一年用几次的功能不该因为一个月没人用就退回未知。

### 6.2 判定

开关是 `objects.ask_unknown_functions`，一个布尔项，默认关，与 `functions` 并列（写 T4 规划时从 `objects.learning` 里挪出来的：它是判定的设置，不是学习的设置，而且控制台的学习设置表单要求 `learning` 里每个键都在）。不用“功能表非空就启用”这种隐式规则，是因为只想用第 2 层的站点会手写一两条管理档条目，那不代表它有一份完整的基线。功能表为空时不允许打开开关。

开关打开后，请求的功能不在已知功能里时（路径无法化为规范拼写的也算）：

- 不快速放行。原本会交 Jev 的请求照旧交 Jev。
- `state.request` 带上 `"function": {"known": false}`。`access` 问题的指令补一段：本站正常流量没有用过这个方法和路径；指向管理、运维、调试、监控、内部接口、目录和文件列表、批量导出或删除的，答 DENY；与本会话近期请求同类的普通页面或接口，答 ALLOW。不新增第三个问题。指令文字变了，提示词版本号对所有站点都会变，和档位那次一样。
- Jev 判放行的，可以写放行缓存（同一会话同一请求 10 分钟内不再问），否则一个不在基线里的轮询接口会把会话的调用额度用完。
- Jev 判拒绝、超时或答 UNKNOWN 的，按现有规则处理（拒绝，或按 `on_jev_unavailable`）。
- 判定记录写 `trace.function.known = false`。

没人走过的功能不是直接拦，是不再免检。这和 11-03 定的“无证据本身不拦”一致。

### 6.3 这一层靠的是模型

假 Jev 只能验证流程，验证不了判断质量。你在 11-13 提供了密钥，我用指令草稿直接问了真实 Jev，结果在第 16 节。要点：运维、调试、管理类路径它判得稳；指令的措辞影响很大，第一版草稿把新出现的普通接口也判了拒绝，改写后才正常；名字普通的管理接口（`GET /api/Users`）它认不出来，那是第 2 层的事。

## 7. 对放行和拦截结果的影响

拦截模式下。“现在”指 `ad1a8e6`。

| 请求 | 现在 | 之后 | 层 | 前提 |
|---|---|---|---|---|
| 假凭证，非入口，没有请求值 | 快速放行 | 401 | 1 | 无，所有站点 |
| 假凭证，非入口，有未见值 | 交 Jev（空上下文） | 401 | 1 | 无 |
| 假凭证，先访问公开入口再访问别处 | 快速放行 | 401 | 1 | 站点声明了用户身份位置；没声明的不变 |
| 真会话，网关重启后第一个请求落在非入口 | 无值的快速放行，有值的交 Jev | 401，直到被重新认可 | 1 | 无（误拦风险，见 8.1） |
| JSON 登录后第一个请求落在非入口 | 放行，但会话不带登录值 | 绑定成功，带登录值 | 1 | 无（变好） |
| 普通用户调已确认的管理功能，值都见过或没有值 | 快速放行 | 交 Jev 要求 DENY，拦截 | 2 | 站点有角色身份位置，功能已确认为管理档且可靠性高 |
| 管理员调同一功能 | 快速放行 | 不变 | 2 | |
| 管理员会话还没声明过角色时调管理功能 | 快速放行 | 拦截，直到身份响应声明角色 | 2 | 同上（误拦风险，见 8.2） |
| 任何会话调功能表之外的功能，值都见过或没有值 | 快速放行 | 交 Jev，模型决定 | 3 | 站点打开了开关 |
| 没带凭证，对入口路径用没人走过的方法，没有未见值 | 快速放行 | 交 Jev，模型决定 | 3 | 同上 |
| 已知功能上的其他请求 | | 不变 | | |
| 没有功能表、没开开关的站点上，除第 1 层以外的一切 | | 不变 | | |

观察模式下，上面的“401”“拦截”都变成转发并记“本应拦截”；第 3 层的 Jev 调用是真实发生的。

## 8. 误拦风险

### 8.1 第 1 层

| 场景 | 后果 | 缓解 |
|---|---|---|
| 网关重启或发布，会话全空 | 已加载的单页应用继续调接口，全部 401，多数应用会跳回登录页。比现在更重：现在无值的请求还能过 | 身份站点：应用启动时调的身份接口是入口，就能靠 S3 认回，不用重新登录。根治要等 P1-6（会话落库）。第 1 层让 P1-6 更值得做 |
| 身份接口没登记为入口 | 重启后只能靠重新登录认回；登录时不换会话 Cookie 的源站上，用户会一直被拦到清 Cookie | 保存站点时提示“身份位置所在接口不是入口”；现有的入口建议（`entry_candidate`）会在观察模式下把它列出来 |
| JSON 令牌刷新 | 新令牌未认可，每个刷新周期全员 401 | P1-1 必须先修或同时修（4.2） |
| 待绑定登录被挤掉或过期（5 分钟、1000 份） | 登录高峰时部分用户的令牌绑定不上 | 身份站点靠 S3，其他站点靠 S4，都要求下一个请求是入口。观察模式下看 `login_expired`、`login_unmatched` 的数量 |
| 网关闲置 24 小时回收了会话，源站会话还在 | 与重启相同，只影响这一个用户 | 同第一行 |

### 8.2 第 2 层

| 场景 | 后果 | 缓解 |
|---|---|---|
| 冷门功能被提议成管理档，你确认了 | 普通用户用它时被拦 | 提议必须人工确认，提议里显示证据（几个管理员单位、全站多少活跃用户、多少人被源站拒绝）；确认前用影响预估回放过去的请求；判定只用可靠性 `high` 的条目；可以随时去掉条目的管理档 |
| 站点的管理员角色标签不是 `admin`（如 `ROLE_ADMIN`、`superuser`） | 没有会话被认作管理员，学不出管理档；手写管理档条目会把真管理员也拦住 | 这是现有限制（docs/07 7.4.7）。保存带管理档的功能条目时，如果窗口内没有任何管理员单位，提示这一点。你已决定先不按角色标签泛化 |
| 管理员会话还没见到身份响应（刚登录、重启后） | 管理功能被拦，直到身份响应到达 | JSON 登录响应里的角色在绑定时已经记入；其余情况要求身份接口先于管理功能被调用，通常成立。观察模式下统计“会话无角色时命中管理档”的次数 |
| 角色只在登录时返回、之后没有接口再返回 | 重启后管理员失去角色 | 同上，根治靠 P1-6 |

### 8.3 第 3 层

| 场景 | 后果 | 缓解 |
|---|---|---|
| 源站发版，新增功能 | 交 Jev。模型判 ALLOW 则只多一次调用；判 DENY 就是误拦，而且因为没人成功走过，学习永远不会提议它 | 控制台把“被拦的未知功能”列为建议，一键加入功能表；发版前可以手工加 |
| 路径里的标识不是数字或 UUID（`/users/alice`、`/products/PT-7004`） | 每个取值是一个不同的“功能”，永远攒不够单位 | 学习时合并：同一方法、同一前缀下，很少人用的兄弟段达到一定个数时归为 `{id}`（含数字的取值 10 个起，纯字母的 50 个起，免得把路由词合并掉；规则见 T2 规划 2.4）。这也是 docs/01 1.3 里“按站点学习路由词”那个已知缺口 |
| 没进 `bypass` 的静态文件，文件名带哈希 | 每次发版都是新功能 | 同上一条的合并；现有的 `bypass_candidate` 建议 |
| 基线里漏了低频功能 | 交 Jev，模型决定 | 确认基线时未达阈值的功能也列出来供勾选；影响预估显示会受影响的请求 |
| Jev 调用量上升 | 延迟和费用；扫描器会更快用完会话限额 | 放行可缓存；限额超出在 P0-2 修完后是 429。具体多多少看第 10 节的数据 |
| 基线被污染：有人在基线形成之前用几个账号反复访问 `/metrics` | 它出现在基线候选里 | 基线必须人工确认；身份站点只按有身份的用户计数；候选按单位数从少到多排，敏感路径词标出来 |

## 9. 迁移和上线顺序

- **数据库**：一次迁移（0011），把 `object_response_evidence.kind` 的取值约束放宽，增加按功能记“走过”的类型。这张表已经在按路由存“被拒绝”的记录。不新增表，不回填，旧行不变。
- **站点配置**：`objects.functions` 和 `objects.ask_unknown_functions` 都是可选的，省略即现在的行为，旧配置不用改。导入导出和回滚照常工作。
- **第 1 层没有开关。** 它对所有站点生效，靠站点的观察模式做缓冲。评审的建议本来就是所有站点先留在观察模式，所以不为它单加一个配置项。
- **判定记录**：新增 `trace.function`，带 `#[serde(default)]`，旧记录照常读入。
- **提示词版本**：`ACCESS_INSTRUCTIONS` 增加一段（第 16 节的草稿三），DENY 选项的含义改一句，版本号对所有站点变化；没有功能条目的站点 `state` 的数据不变。
- **文档**：docs/00 的 0.2、0.3、0.6，docs/01 的 1.2、1.4、1.7，docs/02 的 2.2，docs/03 的站点配置，docs/04 的验收场景，docs/06、07 的对象表和就绪检查，以及 `CHANGELOG.md`。docs/00 0.3 “只接受正常访问路径”的说法在三层做完之后才与实现相符。

## 11. 做不到和不做的

- **同一角色内的功能区分。** 两个医生一个能开处方一个不能，网关分不出来。
- **没有角色身份位置的站点上的第 2 层。** 网关不知道谁是管理员，就没法只对管理员开放。这类站点只有第 1、3 层。而第 3 层挡不住管理功能，因为管理员自己在走，它是已知的。控制台在发现“只有极少数用户在用的功能”时提示去声明角色身份位置。
- **匿名会话调登录后的普通功能。** 在给匿名访客发会话 Cookie 的站点上，匿名会话调一个普通用户都在用的功能，三层都不拦，由源站自己的登录检查负责。可以再加一个“需登录”档来管，本稿不做，先在就绪检查里统计“只有带身份的会话成功走过、却被无身份会话访问”的次数，有数据再定。
- **GraphQL 和把操作名放在客户端可随意填写的字段里的接口。** 功能键能区分的前提是接口名可信。
- **功能的参数级权限**（同一接口，传 `scope=all` 才是管理操作）。这是批量赋值一类的问题，属于评审稿的 P2-1。
- **偷到管理员凭证的人。** 与 docs/00 0.6 相同。

## 12. 新增项和理由

AGENTS.md 要求新增配置项、表之前先确认现有机制不够用。

| 新增 | 为什么现有机制不够 |
|---|---|
| `objects.functions[]` | 对象表条目描述的是值的位置，必须带类别；没有地方能记“这个接口本身只给管理员”或“这个接口是本站的正常功能”。字段和取值全部沿用位置条目的 |
| `objects.ask_unknown_functions` 开关 | 第 3 层改变所有无值请求的去向，必须等站点有完整基线才能开，不能做成代码默认值，也不能从“功能表非空”推断（6.2） |
| 迁移 0011：放宽 `object_response_evidence.kind` 的约束 | 这张表已经按路由存“被拒绝”的单位，功能的“走过”是同一类数据，不另建表。管理档提议优先复用 `object_tier_judgements`；实现规划时核对它的清理逻辑，装不下再在 PR 里说明 |
| `trace.function`、`trace.unrecognized_credential` | 就绪检查和影响预估要按功能、按未认可凭证计数；不进 `decision_log` 的列 |
| `state.request.function` | Jev 要知道功能是不是已知、是不是尝试越权 |

不新增：表、环境变量、crate、判定路径的枚举值、Jev 的问题数量。

- 两版都没拦住的：`GET /api/Users`（列出全部用户）。路径只是一个集合名，模型看不出它是管理接口。这类只能靠第 2 层的管理档。
- 草稿三没拦住 `GET /trace`（ALLOW 0.50，接近平局）。
- 两版都误拦的：`GET /api/config/ui`（前端取界面配置，被当成配置接口）。草稿二另外误拦了 `GET /api/patients/{id}/export-pdf` 和 `GET /api/wards/occupancy`（0.57）。
- `GET /redirect?to=https://…` 的 `access` 答了 ALLOW，但 `attack` 答了 ATTACK，仍会被拦。
- 单次调用中位数约 160 毫秒，最长 406 毫秒。

**结论**

1. 第 2 层的“尝试越权要求 DENY”，模型照做：草稿二、三各 4 例，8 次全是 DENY，概率不低于 0.99，包括名字完全看不出是管理接口的。
2. 第 3 层对运维、调试、泄露类路径有效，这正是它要兜的范围。对名字普通的敏感接口无效，设计里本来也不指望它。
3. 第 3 层会误拦一部分名字像配置、导出的新接口，这个样本里是 20 个里 1 到 3 个。所以“被拦的未知功能”建议和一键加入功能表（8.3）不是可选项，要和判定同一批上线。
4. 接近平局的答案（0.50 到 0.63）有好几个，方向有对有错。你已经决定做置信度门槛（P2-2），这些用例可以直接用来定门槛。
5. 用草稿三作为实现的起点。这 75 个用例整理进 `live_jev.rs`，以后改指令时回归。样本是我编的，不代表真实站点的分布，步骤 D 的观察数据仍然需要。
