# 设计稿：源站换发凭证后沿用原会话（评审稿 P1-1）

- 状态：已确认（2026-11-13）。第 10 节的问题按建议定：沿用原会话，按第 4 节的四条边界断开。C1 的实现规划见 [credential-rotation-plan-c1.md](credential-rotation-plan-c1.md)。
- 基线：`main` `0acae80`。依据：[waf-strategy-review.md](../answers/waf-strategy-review.md) 的 P1-1，以及 [function-level-authz.md](function-level-authz.md) 第 4 节（第 1 层）。
- 第 10 节的问题已有答复，记在该节末尾。

## 1. 结论

现在的规则是“凭证变了就是新会话，上下文从空开始”（docs/01 1.2）。源站自己给同一个人换发凭证时，这条规则会误伤：

- 短期 JWT 加刷新的站点，每隔十几分钟全员的上下文清零一次，之后访问刚才还能快速放行的对象都要问 Jev，多数被拒。
- 每个响应都重发会话 Cookie 的框架（Laravel 默认把会话 Cookie 加密后下发，密文每次不同；ASP.NET 滑动过期会重发票据），每个响应都开一个新会话，网关在这类站点上基本不可用。
- 第 1 层上线后更严重：JSON 接口刷新出来的新令牌是“未认可的凭证”，非入口请求直接 401。

建议改成：**源站在给一个会话的响应里换发的凭证，是同一个会话的另一把钥匙**。网关里一个会话可以对应多个凭证，上下文、身份、放行缓存、Jev 额度都只有一份。重新登录、退出、换账号仍然是新会话，靠第 4 节的四条边界断开。

不做的事：按用户身份把不同浏览器的会话并到一起。新浏览器登录仍然是新会话，这条不变。

## 2. 现状（`main` 上读代码和评审时的探针）

| 场景 | 现在的结果 |
|---|---|
| 带旧 Cookie 的请求，响应用 `Set-Cookie` 换了会话 Cookie | 新凭证开一个新会话，只带这一个响应的值和旧会话“发出过的值”。旧会话见过的值不带过去。评审探针：换发前 `GET /api/patients/7` 快速放行，换发后同一请求交 Jev 被拒 |
| 凭证在请求头里，响应用同名响应头换发 | 同上 |
| 凭证在请求头里，新令牌在刷新接口的响应 JSON 里 | 网关不知道 JSON 里哪个值是凭证。新令牌第一次出现时没有会话：PR 193 之后按空会话判，第 1 层之后非入口 401。只有“没带凭证的入口请求”的 JSON 响应才会被暂存（登录绑定），带着旧令牌去刷新的不算 |
| 刷新请求不带旧令牌，只带刷新令牌（请求体里，或单独的 httpOnly Cookie） | 同上，而且请求本身没有会话可以挂 |
| JSON 登录返回的令牌超过 128 个字符（JWT 基本都是） | 登录绑定从未生效：响应提取丢弃超过 128 个字符的标量，令牌进不了凭证候选，绑定永远对不上。这是现有功能的缺陷，不等本稿确认，单独先修，规划见 [login-binding-long-token-plan.md](login-binding-long-token-plan.md)（C0） |
| 每个响应都换 Cookie | 每个响应一个新会话。会话表、按会话计的学习阈值、按会话计的 Jev 额度都被冲散 |

## 3. 规则

用词：**上下文**是网关为一个会话记的全部东西（已见值、发出过的值、近期请求、经过的入口、身份、放行缓存）。**凭证**是请求上那个 Cookie 或请求头的值。现在一个凭证对应一个上下文；改完后多个凭证可以指向同一个上下文，后来的叫**别名**。

### 3.1 一个上下文，多个凭证

- 会话表拆成两层：凭证的键控哈希指向上下文编号，上下文编号指向上下文。上下文编号取它第一个凭证的哈希，所以判定记录里的 `session` 标签在换发前后不变，控制台的会话页看到的是一条连续的会话。
- 每个上下文最多 16 个别名，超出时去掉最旧的。旧凭证在被挤掉之前继续有效：刷新的同时还在路上的并发请求带的是旧令牌，它们要落在同一个上下文里。
- 会话表上限（2 万）数的是上下文。闲置 24 小时过期也按上下文算，任何一个别名上有请求都算活动。
- Jev 额度、放行缓存、学习时的会话单位都按上下文算。每个响应换 Cookie 的站点因此不再是“每个响应一个会话”。

### 3.2 什么时候加别名

三种来源，按证据从直接到间接排。每一种都要求不碰到第 4 节的边界。

**R1 响应头或 Cookie 换发。** 请求带着已认可的凭证 X，源站的响应（2xx 或 3xx）用 `Set-Cookie` 或同名响应头下发了另一个值 Y（至少 16 个字符，`deleted`、`guest` 这类固定短值不算换发）：Y 成为 X 所在上下文的别名。这是源站在回答 X 的持有者时亲手给出的新凭证。现在这一步是“给 Y 开新会话并继承发出过的值”，改成加别名之后那段继承逻辑就不需要了。

**R2 响应 JSON 里的令牌。** 请求带着已认可的凭证 X，2xx 的 JSON 响应里有“像令牌的值”：网关把它记为这个上下文**下发过的秘密**。之后某个请求把其中一个值当作凭证带来时，它成为这个上下文的别名。

“像令牌的值”的条件，全部满足：

- 字符串，16 个字符以上、不超过 8 KiB。超过 128 个字符的走 C0 加的“凭证候选”通道（全是可见 ASCII 的才算），不进已见值；
- 不是这次请求自己发出的值的回声，也不是当前的凭证；
- 所在位置不经过数组（数组里的是列表，不是下发）；
- 形状是 JWT（`eyJ` 开头、两个点分成三段 base64url），或者字段名含 `token`、`jwt`、`session`，或者字段名就是 `sid`（比较时忽略大小写和 `_`、`-`）。

每个上下文最多记 8 个下发过的秘密，按“接口加字段位置”各留最新的一个，所以每个列表响应都带的 `next_page_token` 只占一格，不会把刷新令牌挤掉。只存键控哈希和位置，不存原文，随上下文一起过期。

登录绑定（docs/01 1.7 的暂存）成功时，登录响应里其余像令牌的值同样记为新会话下发过的秘密，这样登录时拿到的刷新令牌以后能用。

**R3 不带凭证的刷新请求。** 请求没有带凭证，但它的请求体或查询参数里有一个值，是某个上下文下发过的秘密（典型是刷新令牌）：这次响应里像令牌的值记到那个上下文名下，之后按 R2 成为别名。这个请求本身仍按现在的规则判（入口上按地址上下文），R3 只决定响应里的新令牌归谁。

**R3 的 Cookie 形式。** 刷新令牌放在单独的 httpOnly Cookie 里、访问令牌只在内存里，是现在推荐的做法。它需要网关多读两样东西：响应里会话凭证之外的 `Set-Cookie` 值（记为下发过的秘密），和不带凭证的请求上的其他 Cookie 值（用来对上）。都只算键控哈希，不记原文，不进日志，不发给 Jev。

### 3.3 与第 1 层的关系

第 1 层规定“未认可的凭证按没有凭证处理”，认可的依据是 S1 下发、S2 登录绑定、S3 身份声明、S4 入口 2xx。本稿给它加一条 **S5 续期**：凭证是某个活着的上下文下发过的秘密（R2、R3）。R1 就是 S1 落在已有会话上的情形。观察模式下“本应拦截”的响应什么都不认可，这里同样：不加别名，不记下发过的秘密。

## 4. 边界：哪些换发不沿用

沿用的前提是“还是同一个人”。下面四条任意一条成立，新凭证就开一个全新的上下文，不成为别名。

| 边界 | 判断 | 针对的情况 |
|---|---|---|
| B1 身份变了 | 站点声明了用户身份位置，上下文已经有用户，而一个响应声明了另一个用户。原上下文连同它的全部别名作废，得到这个响应的凭证开新上下文，从这个响应学起（写 C1 规划时从“只摘出这一个凭证”改成整个作废：同一条换发链上的旧凭证不该再够得着上一位用户的上下文，实现也更简单）。没有换发时也适用（同一个 Cookie 换账号） | 不退出直接换账号、管理员“以某用户身份登录” |
| B2 主体不同 | 新旧凭证都是 JWT、都有 `sub`，而 `sub`（有 `iss` 时连同 `iss`）不同。只读不验签：旧令牌是源站认过的，新令牌是源站在响应里给的 | 换账号、代登录接口返回别人的令牌、列表里别人的令牌 |
| B3 密码登录 | 得到新凭证的那个请求，请求体或查询里有名字含 `password`、`passwd`、`pwd` 的字段 | 同一浏览器里上一位没退出、下一位直接登录 |
| B4 退出 | 得到新凭证的那个请求，路径最后一段去掉 `-`、`_` 并忽略大小写后是 `logout`、`signout`、`logoff`、`signoff` | 退出时框架发一个新的匿名 Cookie |

B3、B4 是按名字猜的，写在代码里，不做成配置。B1、B2 是确定的。

另外两条保护：

- 一个值已经是别的上下文的凭证时，不改它的归属。一个值已经是某个上下文的别名、又被源站发给另一个上下文时，它是共享的值而不是某个会话私有的凭证：从原上下文摘掉，单独开一个上下文（`trace.response.fresh` 记 `shared`）。这一条是写 C1 规划时补的，防的是源站给所有退出的人发同一个匿名 Cookie 值。
- 别名只沿用上下文，不产生新的权利：管理员身份跟着上下文走，所以刷新令牌之后管理员还是管理员；碰到边界开新上下文时身份从空开始。

## 5. 对放行和拦截结果的影响

| 场景 | 现在 | 改完 |
|---|---|---|
| JWT 刷新之后访问刷新前见过的对象 | 交 Jev，多数被拒；第 1 层之后新令牌在非入口上 401 | 快速放行，和刷新前一样 |
| 每个响应换 Cookie 的站点 | 每个请求都像新会话的第一个请求 | 正常积累上下文 |
| 登录时换会话 Cookie（防会话固定），表单里有密码 | 新会话从空开始 | 不变（B3） |
| 退出后框架发匿名 Cookie | 新会话从空开始 | 标准退出路径不变（B4）；路径名字不标准的站点，匿名会话沿用原上下文，见第 7 节 |
| 管理员刷新令牌后调管理功能（第 2 层） | 新会话没有角色，会被当成尝试越权 | 角色跟着上下文，正常 |
| 换发后的 Jev 额度 | 每个新凭证一份新额度 | 同一个上下文一份 |
| 别人的令牌出现在列表里，被拿来当凭证 | 新会话从空开始（第 1 层之后要先过 S3 或 S4） | 数组里的不记；不在数组里的若是 JWT 且主体不同，B2 断开；其余情况成为持有者自己上下文的别名，拿不到别人的上下文，身份响应一来 B1 断开 |

没有换发凭证的站点，判定和日志与现在逐字相同。

## 6. 误拦和漏拦的风险

- **误拦减少**是这项改动的目的，没有新增的误拦路径。碰到边界时的行为就是现在的行为。
- **漏拦**：沿用上下文意味着新凭证能快速放行旧凭证见过的值。新凭证只可能来自“源站回答旧凭证持有者的响应”，所以拿到新凭证的人本来就握着旧凭证，没有多出能力。真正要防的是“同一台电脑上换了人”，由第 4 节的边界处理，剩下的缺口在第 7 节。
- **伪造**：别名和下发过的秘密都只从源站的响应里来，请求里自己写一个值不会变成别名。R3 里拿来对上的值必须是源站此前在响应里给过这个上下文的。
- **容量**：别名每个上下文 16 个，下发过的秘密 8 个，两张索引表的条目数有上限，带编造凭证的请求只做一次哈希查找。

## 7. 做不到和已知缺口

- **退出路径名字不标准，且每个响应都换 Cookie 的站点**：退出后的匿名会话沿用上一位的上下文和身份，直到下一次密码登录（B3）或身份响应（B1）。利用它需要坐到那台电脑前，而且源站对匿名请求不做登录检查。
- **没有用户身份位置，又用单点登录（回调里没有密码字段）的站点**：共享电脑上，下一位登录后沿用上一位的上下文，B1 和 B3 都帮不上。这类站点应当声明用户身份位置，控制台的就绪检查里提示。
- **刷新接口既不带旧令牌、也不带网关见过的刷新令牌**（比如刷新令牌由移动端本地保存、从没经过网关）：新令牌对不上任何上下文，按第 1 层的未认可凭证处理，和现在一样。
- **网关重启**后别名和下发过的秘密都丢失，和上下文一样，用户从入口重新进入。
- 不验 JWT 的签名，也不读 `exp`。源站认不认一个令牌由源站说了算。

## 8. 新增项和理由

| 新增 | 为什么现有机制不够 |
|---|---|
| 会话表的两层结构、别名、下发过的秘密 | 现在凭证和上下文一对一，换发只能开新会话 |
| `trace.session.continued`（`issued` 或 `announced`，只在新别名第一次被使用的那条记录上） | 观察期要数“多少会话靠换发延续”，并能在请求详情里解释为什么一个新凭证有旧上下文 |
| `trace.response.fresh`（`identity`、`subject`、`login`、`logout`、`shared`，只在边界断开时） | 观察期要看边界有没有误断或漏断 |
| R3 的 Cookie 形式要网关读会话凭证之外的 Cookie 哈希 | 刷新令牌在 httpOnly Cookie 里时没有别的办法对上 |

不新增：配置项、表、迁移、环境变量、crate、判定路径的枚举值、发给 Jev 的内容。几个上限和名字列表都是代码常量。

文档要改：docs/01 的 1.2（“凭证变了就是新会话”改成本稿的规则和边界）和 1.7，docs/07 的判定记录字段和会话页说明，`CHANGELOG.md`。

## 10. 需要你拍板的问题（已答复）

**源站换发的凭证要不要沿用原会话？** 这会改掉 docs/01 1.2 里“凭证变了就是新会话”的规则。

- **建议：沿用，按第 4 节的四条边界断开。** 解决 JWT 刷新和每响应换 Cookie 的误拦；代价是第 7 节的两个缺口（退出路径不标准的站点、没有身份位置又用单点登录的站点，在共享电脑上会把上一位的上下文带给下一位）。
- 更保守：没有用户身份位置的站点只在新旧凭证都是 JWT 且主体相同时沿用，其余照旧。第 7 节的两个缺口都没有了，但这类站点上不透明的会话 Cookie 换发仍然清零，Laravel 一类的站点要先声明身份位置才能用。
- 不改：保持现状，P1-1 不修。

**答复（2026-11-13）：按建议。** 沿用原会话，按第 4 节的四条边界断开；第 7 节的两个缺口作为已知局限写进文档，控制台的就绪检查提示没有用户身份位置的站点。实现顺序不变：C1 在第 1 层（T1）和 WAF 批次 5 合入之后开工，C2、C3 依次在后。
