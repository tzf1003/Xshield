# 搜索泄露 ID 后的越权修改：当前代码能否拦截

- 日期：2026-11-03
- 代码基线：仓库 HEAD `b955771`（v4 判定路径，`crates/xshield-judge`）
- 靶场：新增 A9（`scripts/test_idor_lab.py`），全部 65 项检查通过，EXIT=0

## 结论

**不能拦截。** 搜索接口把别人的用户 ID 返回给当前会话后，对这些 ID 的修改请求（PUT、PATCH、DELETE）会被放行。判定只问两件事：这个值是否被源站展示给过本会话，类别是否相同。判定过程不区分读和写。

这不是实现遗漏，而是现行设计的结果。`docs/00` §0.6 写明：源站在正常界面里多给了数据，之后的访问会被放行，网关"不修复源站自身的授权错误"。`object-map` 设计笔记 §9.3 也写明：搜索接口的真正风险在"返回了谁的数据"，请求侧只能判断这次查询是否合理。

确定会拦的只有一种情况：修改的 ID 从未在本会话里出现过（靶场 A2、A4）。

## 代码路径

1. **核验**，`crates/xshield-judge/src/engine.rs` `plan()`（L376 起）。每个请求值查会话里的已见记录，`verified` 由类别比较得出（L406–413）。搜索返回的 `id` 与详情接口返回的 `id` 没有区别，判定里找不到"来源是搜索"这个信息。
2. **快速放行**，`plan()` L464–467。所有值都已核验、没有截断、路由已知，直接放行，不调 Jev。写请求走同一段代码（`docs/01` §1.5 明文如此）。
3. **方法只出现在两个键里**：位置键 `METHOD route position`（`crates/xshield-judge/src/slots.rs:25`）和放行缓存键（`engine.rs` `cache_key`，L621–643）。前者让 PUT 位置和 GET 位置可以有不同类别，后者让读写的放行缓存互不复用。两者都不构成允许或拒绝的条件。`xshield-judge` 里没有按方法放宽或收紧的分支。
4. **对象表（类别）**：`crates/xshield-core/src/context/objects.rs:225` `class_of`。对象表只回答"请求位置和展示位置是不是同一类对象"，不回答"能不能改"（设计笔记 §5：对象表只决定类别，不决定见过没有）。`shown_as`（`crates/xshield-core/src/kind.rs:232`）按四种情况判断：两边都有类别就比较类别；只有一边有，就看另一边的名字；两边都没有，就看字段名是否像标识、值是否够长，或名字里是否带类别词。
5. **Jev 提示词**，`crates/xshield-judge/src/state.rs:37`（ACCESS_INSTRUCTIONS）。规则是"每个对象值都曾作为同类对象展示给本会话，才能 ALLOW"。搜索结果满足这一条。提示词没有读写区分，也没有"搜索或列表结果只能用于展示"的规则。state 里有 `method` 字段，但指令没有要求据此收紧。真实 Jev 的结论由模型给出，按字面规则应当 ALLOW，但不是确定性保证。
6. **path_confirm**，`crates/xshield-control/src/object_map.rs:354–362`，是控制台的功能开关，表示网关能按位置（方法、路由模板、路径段）使用路径参数的类别。它不改变放行条件。

## 其他会被拦的情况（都不是防护）

| 情况 | 结果 | 依据 |
|---|---|---|
| 修改的 ID 从未在会话里出现 | 拦截，Jev DENY | 靶场 A2、A4 |
| 对象表给搜索位置和修改位置设了不同类别 | 未核验，交给 Jev；Jev 写明两边类别，可能 DENY | `shown_as` 第一种情况；Jev 指令 |
| Jev 超时、出错，或答 UNKNOWN | 按站点 `on_jev_unavailable` 处理，默认拒绝 | `docs/02` §2.3 |
| 观察模式 | 照常转发，只记录"本应拦截" | `docs/01` §1.4 第 7 步 |

第二行是对象表配置的偶然结果，不是设计保证。

## 靶场 A9

医生 B 建两个患者，只有一个的名字能被搜到。医生 A 搜索后执行删除：

| 步骤 | 现状结果 | 判定路径 |
|---|---|---|
| 医生 A 按名字搜索 | 放行，结果含医生 B 的患者 | `jev_allow` |
| 删除搜到的患者 | 放行，源站真的删除 | `jev_allow` |
| 删除没搜到的患者 | 拦截，源站仍保留 | `jev_deny` |

两次删除是同一个动作，唯一的区别是源站是否把这个患者展示给了本会话。靶场没有配置对象表，所以走名字推断加假 Jev 的路径。真实站点里，如果搜索位置和删除位置被确认为同一类别，结果会变成 `fast_allow`，结论不变。

复现：`python3 scripts/test_idor_lab.py --only A9`，或全部运行。A9 记录的是现状。修复后，A9 中搜到的患者的删除要改为拦截。

## 缺口与修复方案（未实施，待确认）

**推荐方案：写操作只认入口或本会话新建的对象。**

- 对 POST、PUT、PATCH、DELETE，一个对象引用只有在以下来源出现过，才算已见：入口请求的响应（即 `entries`，例如"我的患者"）；本会话 POST 创建后源站返回的记录。搜索、查询类响应只能支持读取。
- 不新增配置。入口列表已经存在，符合 `AGENTS.md` 的"做减法"。
- 判定是确定性的，不依赖模型。
- 先在观察模式运行，统计"本应拦截"的请求，检查正常的"搜索 → 编辑"流程会不会被误拦，确认后再切到拦截。
- 靶场 A9 的第一条删除改为预期拦截。

取舍：如果产品上允许"搜到的对象可以直接修改或删除"，这个方案不成立，只能维持现状。

备选方案：

- **只改 Jev 提示词，加读写区分**。结果仍取决于模型，需要评测集，指令版本会变化。
- **响应侧提示**：搜索结果里出现大量本会话没见过的对象时提示（设计笔记 §9.3）。只提示，不拦截。

需要决定的问题：搜到的对象，是否允许直接修改或删除？

## 方案 B 的可行性与误判（2026-11-03 讨论中，未合入）

方案 B 的细化版本已在本地实现并通过测试（judge 163 项，靶场 69/69），按用户要求暂停，未推送。草稿补丁：`answers/search-provenance-draft.patch`。

做法：响应来源标记"是否来自搜索"（路径含 search/find/query/lookup/filter，或查询参数 q、s、wd、kw、search、keyword、term 有值，或打开的对象本身只在搜索里见过）。写操作（POST、PUT、PATCH、DELETE）的目标值必须在搜索之外见过，否则 state 标 `search_only`，Jev 指令要求 DENY。读操作不变。

**会误拦的真实业务**

1. 后台管理：管理员搜到用户后修改、禁用。网关不知道角色，和越权删除在请求上无法区分。
2. 搜索自己的数据再修改：自己的记录很多，靠搜索定位后编辑。
3. 对搜到的公共对象做动作：写评价、回复、预约、加关注。路径里是搜到的对象 ID，实际是创建自己的数据。Juice Shop 商品目录接口 `/rest/products/findAll` 含 find，整个目录会被当成搜索结果，`PUT /rest/products/{id}/reviews` 会被拦（按代码推演，未实测）。
4. 用 POST 做查询的接口（批量取详情、RPC 风格）被当成写操作。

**仍然拦不到的**

- 没有搜索词的列表（全员名录、动态流）展示的别人对象。
- "最近浏览"等不带 ID 的页面重新展示搜到的对象，来源被洗白。
- 过滤参数不叫 q、keyword 的列表接口。

**结论**：能实现，但不适合默认拦截。根本原因是"展示过"不等于"可以改"，网关只能看到展示。

**候选方向**

- A. 只观察：命中时记"疑似越权写"，不拦截，先看真实流量比例。
- B. 站点声明：对象表里给指定写位置标"只认列表或新建来源"，默认不开启。需新增配置字段。
- C. 归属证据：从入口响应学会话自身身份，比对对象上的归属字段（owner、doctor 等）。精度最高，改动最大。

倾向：A 先行，需要拦截时再用 B。

## 相关场景：评论里的用户 ID 拿去访问越权的用户信息接口（2026-11-03）

**会放行。** 用判定引擎做过临时测试（未提交）：`GET /api/videos/V1/comments` 返回后，请求 `GET /api/users/{id}`：

| 评论里的字段 | 值 | 判定路径 | Jev 调用 |
|---|---|---|---|
| `user_id` | `U2023` | `fast_allow` | 0 |
| `author.id` | `98765432`（8 位） | `fast_allow` | 0 |
| `author_id` | `4321` | 交给 Jev（state 带 `seen_as: comments.author_id`） | 1 |
| `mid` | `4321` | 交给 Jev | 1 |

字段名像标识且与路径同类（`affinity`），或值长度达到 `LONG_VALUE_CHARS`（8），`shown_as` 即成立（`crates/xshield-core/src/kind.rs` `shown_as`）。后两行的真实 Jev 结论按指令推断大概率 ALLOW，测试用的是假 Jev。

本质是属性级越权（OWASP API3）：打开评论者主页是正常请求，漏洞在响应多返回了私密字段。请求侧无法区分，需要响应侧检查。现有 `secret_fields` 只作用于发给 Jev 的请求值和日志，不处理返回客户端的响应。

与搜索问题缺的是同一块信息：对象归谁、当前会话是谁。
