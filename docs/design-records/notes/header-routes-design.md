# 接口名不在路径里时怎么判定

2026-11-02 · 设计意见，尚未实现

## 结论

需要调整，做成通用能力：默认用 URL 路径作为接口名（与现在相同）；对接口名放在别处的路径单独写规则，声明真实接口名从哪里取，可以是路径、查询参数、请求头或正文字段。网关把取到的名字拼成一条**逻辑路径**参与判定和记录，转发给源站的请求保持原样。这样入口、绕过、类别推断、放行缓存、判定记录和控制台分组都会按真实接口区分，现有逻辑基本不用改。

## 1. 现在会出的问题

依据：`crates/xshield-edge/src/proxy.rs` 交给判定的 `RequestFacts` 只有 HTTP 方法、路径、查询串、Content-Type、正文和会话凭证；`SiteSpec::matching_entry`、`matching_bypass` 只按路径匹配；`Judge::cache_key` 由 HTTP 方法、路径和请求值组成。以 `/weixin/wx/mp/wx361163d21a65f679/gateway` 这类统一网关为例：

1. **入口和绕过分不开接口。** 整个站点只有一条路径。登记为入口，所有方法都能不登录访问；不登记，登录、换 code 这类本该开放的方法也会被 401。登记为绕过就等于整站不判定。
2. **判定看不到接口名。** Jev 只知道"POST 到 gateway"，不知道调用的是查询还是删除。放行缓存的键里也没有接口名：同一会话 10 分钟内，参数相同的另一个方法会直接复用前一个方法的放行结论。
3. **所有方法共用一个类别。** 类别推断用的是路径里的词，这里所有方法都是 `weixin`、`gateway`。临时测试（未提交）：某个方法的响应是 `{"code":200,"data":[{"id":5}]}` 时，这个 `id` 会让任何其他方法的无名参数 `[[5]]` 直接快速放行，因为两边推断出的类别都是这条网关路径。
4. **控制台按路径分组失效。** 调优建议、本应拦截排行、历史筛选都会把所有方法挤在一条路径下。

## 2. 配置

不写规则时，逻辑路径就是 URL 路径。需要时按路径写规则：

```yaml
routes:
  - path: /weixin/wx/mp/wx361163d21a65f679/gateway   # 与 entries、bypass 相同的路径模式
    name_from:
      - [header.X-Service-Id]
      - [header.X-Service-Method]
  - path: /api/rpc                  # JSON-RPC 一类
    name_from:
      - [body.method]               # JSON 字段，支持 a.b.c；表单正文按字段名
  - path: /index.php
    name_from:
      - [query.action, body.action] # 源站两处都认时写在同一组，出现的值必须一致
```

- `name_from` 的每一组是接口名的一段，按顺序用 `/` 接在路径后面。第一条规则得到 `POST /weixin/wx/mp/wx361163d21a65f679/gateway/bus.buriedPointService/saveBuriedPointList`。
- 来源有四种：`path`（默认，不用写）、`query.<参数名>`、`header.<头名>`、`body.<字段路径>`。
- 同一组里写多个位置，表示源站在这些位置都认这一段：至少出现一个，出现的必须一致。
- 一个请求只按第一条匹配的规则处理；规则的路径互相重叠时保存报错。

拿到逻辑路径以后：

- 入口、绕过直接写逻辑路径，例如把登录方法登记为入口，把埋点方法登记为绕过，其余方法照常判定。
- 放行缓存、判定记录、`seen_as` 里的来源请求、发给 Jev 的 `path` 都用逻辑路径，方法之间不再互相串。
- 用作接口名的那几个值变成路径的一部分，不再作为需要核验的请求值。
- 类别推断从接口名取词（`doctorService`、`getDoctorById` 得到 `doctor`），`get`、`save`、`query`、`list`、`update`、`delete` 这类动词不算类别。
- 判定记录同时保留真实路径和接口名的来源，追溯时都能看到。

## 3. 安全约束

接口名由客户端填写，网关必须和源站读出同一个名字，读不准就按最保守的方式处理。

- **只接受规整的值**：字母、数字、`.`、`_`、`-`，最长 64 个字符。
- **每一段必须恰好得到一个值**：
  - 查询参数、表单字段、请求头出现多次时不取；
  - JSON 正文必须是 JSON 类型并且能解析；字段路径上出现重复的键时不取，因为解析器对重复键的取舍不一样（有的取前一个，有的取后一个）；路径上遇到数组（批量调用）时不取；
  - 正文加密、超过解析上限时不取。
- **取不到就是"未知接口"**：任何一段取不到或不合规，请求都按同一条固定的"未知接口"逻辑路径处理：永远不算入口，不走绕过，交给 Jev，记录里注明原因。
- **源站认的位置都要写上**：源站如果在多个位置都接受接口名（请求头和查询参数都行），必须把这些位置写进同一组，否则可能出现网关按 A 判、源站执行 B。控制台在规则里只写了一个位置时提示这一点。
- **规则只能收紧**：没写规则的路径行为不变；写了规则的路径，取不到接口名的请求只会更严格，不会因为规则多放行。

不适用的情况：

- **GraphQL**：`operationName` 只是客户端起的名字，源站执行的是 `query` 正文里的内容，不能当作接口名，需要单独设计。
- **批量调用**（一个请求里有多个方法）：首版按"未知接口"处理，以后可以拆成多个逻辑请求分别判定。

## 4. 这个站点的几个具体点

- `saveBuriedPointList` 是埋点上报，量大、风险低。按逻辑路径登记为绕过可以省下大量 Jev 调用，代价是这个方法不再做任何判定。
- 路径里的 `wx361163d21a65f679` 是小程序的 AppID，不是对象引用。它在规则的路径里是固定前缀，可以不再当作需要核验的值。
- 样例正文是明文 JSON。如果有的方法正文或响应是加密的（请求头里有 `X-Service-Encrypt`），网关读不到里面的值，这些方法只能交给 Jev，需要单独评估（见 docs/01 第 1.6 节）。
- 正文是位置参数（`[[{...}]]`、`[[5]]`），参数没有名字，类别只能来自方法名。对象表方案（[object-map-design.md](object-map-design.md)）里的位置键会是"逻辑路径 + `body[0][0]`"。

## 5. 改动范围

- `xshield-core`：`SiteSpec` 增加 `routes` 的解析与校验（来源格式、字符集、路径重叠），提供"由请求得到逻辑路径"的函数，网关和控制台共用。
- `xshield-edge`：在交给判定和写记录前算出逻辑路径；`RequestFacts`、`Observation` 带上它，源站请求不变。
- `xshield-judge`：入口、绕过、缓存键、类别推断和响应学习改用逻辑路径；作为接口名的值不再作为请求值核验。
- 控制台：站点详情增加规则编辑；请求列表、调优建议按逻辑路径分组；对"同一路径大量请求、正文或请求头里有类似方法名的字段"给出写规则的建议。
- 测试：登录方法是入口而其他方法不是；两个方法参数相同不共用缓存；第 1 节第 3 条的串类别不再发生；每种来源的缺失、重复、非法字符、JSON 重复键、非 JSON 正文都按"未知接口"处理；同一组多个位置不一致时按"未知接口"处理。
