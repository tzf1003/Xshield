# 缩写字段名的对象归类方案

2026-11-02 · 设计意见，尚未实现

## 结论

- 现在 `doc_id` 真指医生时，网关不会放出越权。只是这类短 id 拿不到快速放行，每个新医生页多一次 Jev 调用（部署测试里中位数约 0.55 秒，同一请求 10 分钟内复用结论）。
- 不建议用站点同义词 `["doc","doctor"]`。它按"词"全站双向生效，连接口路径里的词也算，所以站点只要有 `/api/docs` 这样的文档接口，文档 id 就能解锁医生路径。
- 推荐两件事配合：
  1. 新增**字段归类声明** `advanced.field_kinds`：声明"某个字段装的是哪类对象"。只作用于字段名和参数名，单向，覆盖按名字的推断，可限定在指定接口内。
  2. 控制台新增建议 `field_kind_candidate`：从 Jev 的放行记录里找出"某字段的值总被用在某类路由上"，按证据所在的接口给出限定范围的声明，管理员确认后生效。
- 顺带发现一个可利用的绕过，比本问题更急：源站回显的搜索词会被当成"已见长值"，之后用它访问对象不经 Jev。见第 6 节。

## 1. 问题出在哪

短值（少于 8 个字符）要快速放行，必须满足：这个值曾以标识类字段出现过，并且"展示它的字段推断出的对象类别"等于"请求里用它的位置推断出的类别"。两边的类别都来自名字：

- 展示侧：字段名（`doc_id` 得到 `doc`）；裸 `id` 取父对象名（`Products.id` 得到 `product`）；再没有就取返回它的接口路径（`GET /api/docs` 里的 `id` 得到 `doc`）。
- 使用侧：参数名（`?doctorId=` 得到 `doctor`）；路径参数没有名字，取整条路径的词（`/doctor/2` 得到 `doctor`）。

名字推断有两类错误，#112 只解决了其中一类：

- **缩写**：`doc` 指 `doctor`。#112 之后两词不再相等，结果是漏放行，多调一次 Jev。安全，只是贵。
- **同形异义**：同一个词在站点里指两类对象（`doc_id` 指医生，`/docs/` 指文档）。两边都是 `doc`，精确比较也判它们相等，结果是错放行。名字本身没有信息区分它们，只能靠声明或证据。

实测（在当前 main 上写临时测试调用 `Seen::is_specific`，测试未提交）：

| # | 会话见过 | 请求 | 现在 | 加同义词 `doc`/`doctor` |
|---|---|---|---|---|
| A | 医生 `doc_id: 2`（`GET /api/appointments`） | `/doctor/2` | Jev | 快速放行（预期） |
| B | 文档 `id: 5`（`GET /api/docs`） | `/doctor/5` | Jev | **快速放行（越权）** |
| C | 医生 `doc_id: 2`（`GET /api/appointments`） | `/docs/2`（文档） | **快速放行（越权）** | **快速放行（越权）** |
| D | 文档 `attachments.doc_id: 5`（`GET /api/records/7`） | `/doctor/5` | Jev | **快速放行（越权）** |
| E | 医生 `doctor_id: 2` | `/api/schedule?doc=2` | Jev | 快速放行 |
| G | HTML 里的 `<a href="/doctor/2">` | `/doctor/2` | Jev | Jev |

B 说明同义词的风险比"同一站点用 `doc_id` 表示两种东西"更大：只要有 `/api/docs` 这样的路径就够了。C 是 #112 的镜像问题：站点用 `doc_id` 表示医生、又有 `/docs/` 文档接口时，现在不加任何配置就会错放行。

## 2. 候选方案对比

| 方案 | doc 指医生时能快速放行 | 会不会错放行 | 管理员成本 | 实现成本 |
|---|---|---|---|---|
| 0. 不配置，交给 Jev（现状） | 否，每个新值一次 Jev | 不新增；C 已存在 | 无 | 无 |
| 1. 同义词 `doc`/`doctor`（已有） | 是 | 会：B、C、D | 低 | 无 |
| 2. 单向别名（`doc` 只算 `doctor`） | 是 | 会：B、D 照旧（路径词 `docs` 仍被映射），C 不变 | 低 | 小 |
| 3. 字段归类声明（推荐） | 是 | 范围写对时不会，并堵住 C；同名字段指两种东西却不写范围时会（D） | 中；有建议后低 | 中 |
| 4. 控制台按证据推荐声明（推荐） | 自动发现候选 | 管理员确认才生效，默认带范围 | 低 | 中 |
| 5. 链接共现 | 仅源站给出链接的页面 | 有回显风险（见第 5 节） | 无 | 小到中 |
| 6. 按值集合重合推断 | 短整数 id 无区分力 | — | 无 | 高 |
| 7. 网关学到就自动生效 | 是 | Jev 一次误判变成全站规则，可被刷 | 无 | 高 |

关键不在方向，在粒度和范围：同义词错在把"字段名里的 `doc`"和"路径里的 `docs`"当成同一个东西，而且全站生效。

## 3. 推荐一：字段归类声明 `advanced.field_kinds`

```yaml
advanced:
  field_kinds:
    - field: doc_id                   # 响应字段名或请求参数名
      kind: doctor                    # 它装的对象类别，与路径里的词比较
      in: ["/api/appointments*"]      # 可选：只在这些接口里成立；省略为全站
```

语义：

1. **只认字段名和参数名，不认路径词。** 响应里的 `doc_id`、查询或表单参数 `doc_id`、JSON 请求体字段 `doc_id` 受影响；`/api/docs` 里的 `docs` 仍按名字推断为文档，所以 B 不会发生。请求参数本身用缩写时（E 的 `?doc=2`），另写一条 `field: doc`。
2. **单向。** 声明的是"这个字段装的是医生"，不是"doc 和 doctor 是一回事"。
3. **覆盖，不是追加。** 命中声明的字段只算 `doctor`，不再同时算 `doc`，所以 C 被堵住。
4. **范围。** `in` 用与 entries、bypass 相同的路径模式。展示侧按"返回这个值的请求"匹配，使用侧按当前请求匹配。D 这类"同名字段在别的接口里指文档"的情况靠它隔开。
5. 声明过的字段一律视为标识字段，字段名不像 id 也算（例如 `doc`）。
6. 字段名比较时忽略大小写和 `_`、`-`（`doc_id`、`docId`、`DocID` 是同一个）。裸 `id` 比较的是父对象名（`doc.id` 看 `doc`）。

按第 1 节的场景，声明后的预期行为：

| # | 情况 | `doc_id` 归为 `doctor`，全站 | 加 `in: ["/api/appointments*"]` |
|---|---|---|---|
| A | 医生 `doc_id`（预约接口）用在 `/doctor/2` | 快速放行 | 快速放行 |
| B | 文档 `id`（`/api/docs`）用在 `/doctor/5` | Jev | Jev |
| C | 医生 `doc_id`（预约接口）用在 `/docs/2` | Jev | Jev |
| D | 文档 `attachments.doc_id`（病历接口）用在 `/doctor/5` | **快速放行（越权）** | Jev |
| D' | 同上，用在 `/docs/5` | Jev（多一次调用） | 快速放行 |

D 一行说明：站点里同名字段指两种东西时，必须写 `in`。控制台的建议默认就带上证据里的接口（见第 4 节）。

校验（沿用 `SITE_CONFIG_ADVANCED_INVALID`）：最多 32 条；`field` 1 到 32 个字符，字母、数字、`_`、`-`；`kind` 3 到 24 个小写字母，按 `kind_words` 的规则去掉结尾的 `s`；`in` 最多 8 个路径模式；同一字段在重叠范围内给了两个类别时报错。保存时规范化排序，只改顺序不产生新版本。

与 `synonyms` 的关系：保留兼容，行为不变。控制台把同义词标为"全站双向，范围最大"；同义词里的词也出现在站点路径里（例如 `/api/docs`）时提示 B 类风险，并提供改写成字段归类的入口。内置的 `payment`/`card` 暂不动。

判定代码的改动集中在 `context.rs` 的 `is_specific()` 和 `affinity()`：取展示侧、使用侧的类别前先查声明，命中的字段同时视为标识字段。`Tuning` 增加解析好的声明列表，与 `synonyms` 一样在加载时处理一次。发给 Jev 的输入不变。

## 4. 推荐二：控制台按证据推荐（`field_kind_candidate`）

数据已经在判定日志里：每条记录的 `trace.values[]` 有值的位置、`seen`、`verified` 和最多 3 个来源（字段名和返回它的请求），Jev 记录有结论。

规则（阈值为初始值，上线后按误报调整）：

1. 取时间窗内 Jev 判定过的请求，挑出类型为 reference、已见、未核验、少于 8 个字符的值。
2. 目标是"路径模板 + 值的位置"（`GET /doctor/{id}` 的 `path[1]`，或参数名）；来源是"标识类来源的字段名 + 其请求的路径模板"（`doc_id @ GET /api/appointments`）。
3. 同一组（目标，来源）满足以下全部条件才建议：Jev 放行至少 20 次，来自至少 5 个会话，没有拒绝；该目标被 Jev 判定的请求中至少 90% 带这个来源，用来排除碰巧同值的字段（数量、年龄）；来源字段按名字推断的类别与目标不同，否则本来就会放行。
4. 动作：追加 `{field: doc_id, kind: doctor, in: ["/api/appointments*"]}`，范围默认只含证据里的接口。同一字段在不同接口流向不同类别的目标时，按接口分别建议；同一接口的同一字段流向多类目标时不建议，那是真正的歧义，留给 Jev。

应用前的影响预估：

- 时间窗内有多少次 Jev 调用会变成快速放行；
- 有多少次快速放行会改回调用 Jev，因为该字段不再按原名字归类。这一项正好把 C 类错放行列出来；
- 同一字段还出现在哪些接口的响应里（取自响应摘要的字段名），作为是否放宽 `in` 的参考。

防投毒：只建议，不自动生效；要求多个会话、零拒绝；附示例请求 ID 供管理员抽查。攻击者想刷出有害的声明，得先让 Jev 在多个会话里连续误判；声明会把这种误判放大成规则，所以必须由人确认。

实现上要把类别匹配函数（`kind_words`、`kind_of`、`related`、`affinity`）从 `xshield-judge` 移到 `xshield-core`。控制台现在不依赖 judge，影响预估必须和网关用同一份代码，否则预估与实际不一致。顺带，现有的 `SYNONYMS_CHANGED` 也能从"无法预估"变成按日志近似预估（来源只记了 3 个，所以是近似值）。

## 5. 链接共现，以及不推荐的做法

**链接共现**：HTML 里的 `<a href="/doctor/2">` 现在被拆成 `link=doctor`、`link=2` 两个值，结构丢了，所以短 id 照样走 Jev（第 1 节的 G）。改为记录整条链接路径、请求路径与之完全相同就核验，可以完全不看名字。但它和第 6 节是同一类风险：用户能让源站回显任意链接（评论、留言），网关分不清哪些链接是源站生成的。建议等回显问题修好后再评估。它也帮不了单页应用：那类前端用 `doc_id` 自己拼 URL，响应里没有链接。

**不推荐**：

- 单向别名：问题在粒度和范围，不在方向，B 和 D 照样错放行，C 不变。
- 按值集合重合推断（`doc_id` 的值是否都落在医生 id 集合里）：短整数 id 在医生和文档里都是 1 到 N，重合度没有区分力；长 id 本来就直接放行，用不上。
- 网关自动学习并立即生效：一次 Jev 误判会变成全站规则，同一账号登录多次就能凑出多会话证据。
- 多态引用（`target_type` + `target_id`）：类别取决于另一个字段的值，无法静态声明，继续交给 Jev。

## 6. 顺带发现：回显的搜索词让长 id 绕过 Jev

复现（临时测试，走完整的 `judge` 和 `observe`，Jev 用假实现回答放行，测试未提交）：

1. 会话请求 `GET /api/search?q=P-0000099`。`q` 是搜索词，按提示词属于输入，Jev 放行。
2. 源站返回 `{"query":"P-0000099","results":[]}`，网关把 `P-0000099` 记为已见值（字段 `query`）。
3. 会话请求 `GET /api/patients/P-0000099`：值有 9 个字符，长值"已见即可"，结果是 `fast_allow`，没有调用 Jev。

原因：长值规则假设"响应里的值是源站交给这个会话的"，但搜索、表单、留言会把用户自己输入的值原样带回。患者号这类带前缀的顺序编号很好猜，所以可以利用。

修复方向（需要单独评估多出的 Jev 调用）：

- 长值也要求来自标识类字段，`query`、`text`、`note` 这类字段里出现的长值不再算已见；
- 记录会话自己发出、且未核验的值，源站回显这些值时不算已见。跨会话回显（一个会话写留言、另一个会话读）需要按站点或按账号记录，另行考虑。

## 7. 落地顺序

1. **回显修复**（另开线程，优先级最高）：这是现成可利用的绕过，见第 6 节。
2. **字段归类声明**：`xshield-core` 增加 `field_kinds` 的解析与校验；`context.rs` 在 `is_specific()`、`affinity()` 里应用；控制台站点详情增加表单和本地校验。测试至少覆盖第 3 节表里 A、B、C、D、D' 五行，以及字段名大小写和分隔符、裸 `id` 取父对象名、`in` 同时作用于展示侧和使用侧。
3. **证据建议与影响预估**：类别匹配函数移到 `xshield-core`；`insights.rs` 增加 `field_kind_candidate`；`preview.rs` 的影响预估覆盖 `field_kinds`，并对已有同义词给出 B 类风险提示。
4. **链接共现**：回显修复之后再评估是否做。
