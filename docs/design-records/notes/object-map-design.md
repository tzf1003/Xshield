# 对象表学习方案

2026-11-02 · 设计意见，尚未实现 · 接 [field-kinds-design.md](field-kinds-design.md)

## 结论

- 可行，方向也对。这里把"权威 id"定义为**参数位置指向的对象类别**（例如 `doctor`），不是某条记录的 id。对象表就是"位置到类别"的映射，由规则和 agent 学习、管理员确认。
- 判定时，如果请求里的位置和展示这个值的位置都有已确认的类别，网关直接比较，相同就放行，不同就交给 Jev 并写明两边类别，不再靠名字猜。只要有一边没学到，就退回现在的名字推断，所以新接口不会比现在更差。
- 三个难点：
  1. **新接口**：没学到的位置照现在的方式判，同时记录证据；证据够了先用规则判，判不了再交给 agent。收紧自动生效，放宽要人确认。
  2. **agent 的上下文**：不给"完整日志"，给结构和统计：这个位置的字段结构、系统算好的值流向、几个候选类别的卡片。agent 只能在候选里选，或者回答"新类别"或"有歧义"。
  3. **恶意数据**：对象表只决定"是不是同一类"，不决定"有没有见过"。不存在的 id 从来没被源站展示过，对象表怎么写都不会快速放行。学习只用源站认可的证据（请求被放行且源站返回 2xx），并要求多个会话。
- 实测又发现一处问题：路径参数的类别取的是整条路径的词，不看位置。会话见过医生 7 和 9，就能快速放行 `/api/doctors/7/files/9`，其中的 9 其实是文件。对象表按位置记类别，可以根治这个问题；短期也能单独修（见第 6 节）。

## 1. 对象表是什么

**位置**（slot）是值所在的地方，与具体的值无关：

| 一侧 | 位置键 | 例子 |
|---|---|---|
| 响应 | 接口模板 + 字段路径 | `GET /api/appointments` 的 `[].doc_id` |
| 响应 | 同上 | `GET /api/records/{id}` 的 `attachments[].doc_id` |
| 请求 | 方法 + 路由模板 + 路径位置 | `GET /api/doctors/{id}/files/{id}` 的 `path[4]` |
| 请求 | 方法 + 路由模板 + 参数名 | `GET /api/schedule` 的 `query.doc` |

**类别**（权威 id）是一张卡片：稳定的 id（`doctor`）、名称（医生）、说明、属于它的位置、常见的同级字段（`name`、`title`、`department`）、相关路由。改名不改 id；管理员可以合并、拆分类别。

每个位置有一个状态：`pending`（在攒证据）、`proposed`（规则或 agent 给出了类别，未生效）、`confirmed`（已生效）、`ambiguous`（确实有歧义，例如多态引用，永久交给 Jev）、`suspended`（监控发现异常，暂停使用）、`retired`（长期未出现）。

存储：已确认的部分作为站点配置的一节（例如 `objects`），这样直接复用现有的版本、历史、回滚、网关 5 秒内生效，判定记录的 `site_version` 也能追溯当时用的是哪版对象表。待定位置和证据放单独的表。上一份方案里的 `field_kinds` 就是对象表的手工入口，格式可以统一。

## 2. 判定时怎么用

| 请求位置的类别 | 展示位置的类别 | 结果 |
|---|---|---|
| 已确认 | 已确认 | 相同：已核验（值也必须见过）；不同：未核验，交给 Jev 并写明两边类别 |
| 已确认 | 未学到 | 用请求侧类别与展示侧按名字推断的类别比较（同现在的规则） |
| 未学到 | 任意 | 现在的名字推断，不变 |

发给 Jev 的 `state` 里，值和来源各多一个类别：

```json
{ "at": "path[1]", "kind": "reference", "value": "5", "object": "doctor",
  "seen_as": ["attachments.doc_id @ GET /api/records/7 [document]"] }
```

提示词加一句：`object` 是站点对象表给出的类别，值只以另一类对象出现过时，不算"作为这类对象展示过"。上例 Jev 能直接判越权，不用猜 `doc` 是什么。提示词改了会产生新的指令版本，旧记录不受影响。

底线不变：**值必须被源站展示给这个会话**。对象表只回答"类别是否相同"。

## 3. 难点一：新接口与动态升级

流程：

1. 网关遇到对象表里没有的位置，照现在的规则判定，并在判定记录里写出位置键。
2. 控制台每小时汇总一次（复用现有的后台任务），按位置累计：使用次数、会话数、判定结果、源站状态码、值的流向（这个位置的值之前在哪些响应位置出现过，各占多少）、该接口的响应结构。
3. 达到门槛（例如 7 天内至少 20 次被放行且源站 2xx 的使用，来自至少 5 个会话）后进入学习：
   - **先用规则**：至少 90% 的使用来自同一个已确认类别的响应位置，并且没有拒绝，就直接提议这个类别。便宜，也容易解释。
   - **规则判不了再交给 agent**：没有流向、流向分散，或者名字和结构互相矛盾。
4. 生效策略：**收紧自动生效**，例如把 `doc` 拆成文档和医生，结果只会让一些快速放行改回 Jev。**放宽要人确认**：凡是会新增快速放行的映射，都进入调优建议，附影响预估，一键应用。
5. 漂移：已确认位置的新证据与类别矛盾时，例如流向换了来源、Jev 拒绝变多，就转成 `suspended`，退回名字推断并提示。30 天没出现的位置转成 `retired`。
6. 冷启动：新站点接入时，把名字明确的位置（`GET /api/doctors` 的 `[].id`、`/doctor/{id}` 的 `path[1]`）作为初始提议，在接入向导里让管理员一次确认，后面的学习就有锚点。

网关需要新增两样东西：判定记录里每个值和来源的**位置键**；响应摘要里的**响应结构**，也就是字段路径和类型，不含值。只在某个接口模板的结构签名第一次出现或变化时才记，量很小，接口改版也能顺便发现。路由模板化（数字、十六进制、UUID 段换成 `{id}`）要和控制台用同一份代码，需要移到 `xshield-core`。

## 4. 难点二：给 agent 的上下文

原则：给"对的"上下文，而不是"完整"上下文。完整日志又贵，又会泄露数据，还容易被注入。agent 拿到的都不含值：

```json
{
  "slot": { "side": "request", "method": "GET", "route": "/doctor/{id}", "position": "path[1]" },
  "endpoint_shape": ["id:number", "name:string", "title:string", "department.name:string"],
  "flows_in": [
    { "id": "f1", "from": "GET /api/appointments [].doc_id", "share": 0.87, "uses": 140,
      "sessions": 23, "jev_allow": 140, "jev_deny": 0, "type": null },
    { "id": "f2", "from": "GET /api/doctors [].id", "share": 0.41, "uses": 66,
      "sessions": 12, "type": "doctor" }
  ],
  "candidates": [
    { "type": "doctor", "name": "医生", "fields": ["name", "title", "department"],
      "slots": ["GET /api/doctors [].id"], "routes": ["/doctor/{id}"] },
    { "type": "document", "name": "文档", "fields": ["filename", "mime", "size"],
      "slots": ["GET /api/docs [].id"], "routes": ["/docs/{id}"] }
  ]
}
```

输出受 JSON 结构约束：`choice` 只能是候选里的类别、`new`（附名称和说明）或 `ambiguous`（附原因）；带置信度，并引用依据（`f1`、`endpoint_shape`）。规则和 agent 结论不一致时一律记为 `ambiguous`，交给管理员。

"是已有类别还是新类别"靠**候选召回**解决：按流向重合、字段名相似（含缩写词典，例如 doc、pt、dept）、同级字段的重合度，从对象表里取前 5 个类别；流向涉及的类别一定在内。对象表再大，agent 每次也只看几张卡片。同一位置换了路径（`/api/v1/doctor/{id}` 改成 `/api/v2/doctors/{id}`）时，结构和流向都一致，agent 可以提议"与某位置相同"，直接继承类别。

## 5. 难点三：恶意数据

1. **不存在的 id 不会被放行**：快速放行要求源站把这个值展示给过这个会话。不存在的 id 没被展示过，对象表怎么写都只会交给 Jev，源站也会返回 404。
2. **只用源站认可的证据**：请求被放行、而且源站返回 2xx，这次使用才计数。Jev 拒绝的、没有转发的、观察模式下本应拦截的、4xx 和 5xx 都不算。请求自己带上的值被响应回显时，不算流向证据（与回显问题的修复共用一套记录）。
3. **多样性**：每个会话每天对一个位置最多算一票；要求多个会话，最好是多个账号、多个地址；证据集中在少数来源时降低权重。
4. **容量**：每个接口最多记 64 个参数位置，每个站点的待学位置有上限；只在一个会话里出现过的参数不进学习队列，到期自动清掉；agent 每天有调用预算。乱填的参数只会占用有限的槽位，然后过期。
5. **agent 不被带偏**：输入不含值；请求侧的键名由攻击者控制，带语法字符的（`push_unusual_key` 已能识别）、超长的、字符集以外的一律不进上下文；输出只能在约束内选择。
6. **收紧自动，放宽要人确认**：最危险的错误是错误地放宽，这一步始终有人确认，并附影响预估和示例请求。
7. **上线后自检**：已确认映射带来的快速放行，如果源站返回 403、404 的比例升高，或者同一位置 Jev 拒绝增多，就自动暂停该映射并提示。

## 6. 本次又发现：路径参数不看位置

临时测试（未提交）：会话从 `GET /api/doctors` 看到 `id` 为 7 和 9，请求 `/api/doctors/7/files/9` 时，`path[2]=7` 和 `path[4]=9` 都算已核验，整个请求快速放行。原因是路径参数没有名字，类别取的是整条路径里的所有词（`doctor`、`file`），哪一个对上都算。

对象表按位置记类别，可以根治。短期可以先单独修：路径参数只取紧挨在它前面的路由词（`path[4]` 取 `files`），前面没有路由词时才退回整条路径。这个改动小，可以独立成一个 PR。

## 7. 落地顺序

每一步都能单独上线，没学到的位置行为与现在相同。

1. **先修两个现成的绕过**：回显（见 [field-kinds-design.md](field-kinds-design.md) 第 6 节）和路径参数不看位置（第 6 节）。
2. **对象表骨架**：站点配置增加 `objects` 一节（类别、位置和学习设置），字段归类声明保持在 `advanced.field_kinds`，不并入 `objects`。判定按位置查类别；Jev `state` 带上类别。路由模板化和类别匹配函数移到 `xshield-core`。
3. **证据与规则学习**：网关写出位置键和响应结构；控制台建位置表、流向统计，按规则给建议，接入向导做冷启动确认。
4. **agent 与监控**：处理规则判不了的位置；漂移检测、自动暂停。

## 8. 成本

agent 按位置调用，不按请求调用。一个有 300 个接口、每个接口两三个 id 位置的站点，大约 1000 个位置，大部分由规则解决，agent 首轮可能调用一两百次，之后只在接口变化时零星调用。相比之下，每次快速放行都省掉一次 Jev 调用（部署测试里中位数约 0.55 秒）。

## 9. 复合值与多种搜索方式

现状（临时测试，未提交）：

- JSON 里本来就分开的字段（`{"filter":{"name":"Alice","phone":"138…","id":42}}`）网关已经逐个拆开判断，`filter.id` 被标为对象引用，没有问题。
- 多个值塞进一个字符串（`"who":"Alice#138…#42"`）时，网关只看到一个整体，标为普通输入。里面的 42 不会被当成对象引用，Jev 也被告知这是表单内容、不需要展示过。
- `?by=id&q=42` 这种搜索，`q` 同样被标为普通输入，`by=id` 被当成无关的路由词。按 id 搜索因此等于不做越权判断。

两种情况的共同做法：**把一个值变成若干个有类别的子值，每个子值单独核验；拆不开或对不上，就整体交给 Jev 并写明原因。** 拆分只增加检查，不减少检查，原始值照样参与攻击判定。

### 9.1 复合值：位置带"格式"

- **通用格式，网关直接识别，不用学**：字符串里嵌的 JSON、URL 编码的参数串、Base64 后的 JSON。能解析就按结构展开成子位置，例如 `body.filter{}.doctor_id`。
- **站点自定义的分隔（`name#phone#id`），从证据里学**：网关只上报值的**形状**（字符类别和长度，例如"字母 5 位 # 数字 11 位 # 数字 2 位"），不上报值本身。同一位置在多个会话里形状稳定，就提议"按 `#` 拆成 3 段"，每段再按第 3 节的流向单独学类别：第 3 段的值之前作为患者 id 出现过，这一段就是 patient；前两段是姓名、手机号，属于输入。
- **判定**：按格式拆开后，每段当作独立的请求值（`body.who#2`）核验，任何一段没过，整个请求就不快速放行。形状对不上（段数不对、出现引号等语法字符）时不硬拆，整体交给 Jev 并标注"格式不符"，这类往往正是注入尝试。

### 9.2 多种搜索方式：类别取决于条件

- **有显式开关**（`?by=id&q=42`、`?type=phone&keyword=…`）：对象表记录"`q` 的类别由 `by` 决定"。学习时按 `by` 的取值分组统计 `q` 的流向：`by=id` 时 `q` 的值总是之前展示过的患者 id，就是 patient；`by=phone`、`by=name` 时是输入。
- **没有开关、后端按值的样子判断**（`q=42` 查 id，`q=138…` 查手机号）：类别按值的形状取，例如短数字是 patient，11 位数字是手机号，含字母是姓名。形状到类别的规则同样从流向里学。
- **判定**：取到对象类别（patient）的，按普通引用核验：必须作为患者展示过，否则交给 Jev。取到输入类别（手机号、姓名）的，不要求展示过，但在 Jev 的输入里标成"按身份信息查找"，让 Jev 结合会话判断这种查询是否合理：前台按手机号查患者是正常业务，普通患者查别人的手机号就不正常。
- **学不出规则**（id 和手机号都是纯数字、长度接近，形状重叠）：记为 `ambiguous`，交给 Jev，并把可能的类别都写进输入。

### 9.3 边界

- 恶意构造的值（多一段、带语法字符）不会被硬拆成"合法的几段"，只会整体交给 Jev，攻击判定不受影响。
- 形状只记字符类别和长度，学习过程不接触原始值。
- 搜索接口的真正风险在"返回了谁的数据"，请求侧只能判断这次查询是否合理。以后如有需要，可以在响应侧补一条规则：搜索结果里出现大量本会话从没见过的对象时提示，这是另一个话题。
